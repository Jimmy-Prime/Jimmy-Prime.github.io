M5 Ultra 512GB
本機 LLM 規劃

Coding agent 和長文件分析最吃 prefill 跟 prompt cache。主力先用 DeepSeek V4.1 Flash 1017：experts 和 Engram 查表都維持官方精度不重新量化，Engram 放 SSD，用 oMLX 0.8.0 以上跑 DSpark，CED prefill 0.8.0 起預設開啟。這樣開到原生 1M context，RAM 內的模型也只佔約 290 GiB，還能留 64 GiB 給 prompt cache。512GB 的社群上傳（跟這頁的配置相同：CED 開、A8 關）到 11/25 已有十幾個 session，32K–195K 一直分成兩群：快的 3,525–4,060、慢的 3,009–3,335，正式版 0.8.0–0.8.3 兩群都有，原因不明，所以 prefill 取 3,000–4,050 tok/s。11/26 起主力候選先過一道 benchmark 門檻（DeepSWE 自報 ≥ 70，第三方分數不能低於領先者的一半），只剩 DeepSeek 和 MiniMax M3.1 Flash；GLM-5.3-Flash、Qwen3.8-Flash-Next 移出主力，新的 Inkling 2 Small 放得下但第三方分數和 prefill 都太差，不列入。

硬體與前提

規劃前提

  • 工作負載：coding agent（Claude Code 這類，長 prompt、工具呼叫、多輪重用 prefix）＋長文件分析／RAG。
  • 單一使用者、單一 session 的 KV cache。
  • 一次只載入一個主力模型，512GB 幾乎全給它。
  • Context 先用模型的原生長度，放不下再縮到 256K。
  • 精度優先，其次是 prefill，再來才是 decode。
  • 現有的 M1 Mac mini（16GB）可以當輔助機，但以 M5 Ultra 單機為主。

記憶體上限

macOS 27.2 上 512GB 的預設 Metal 上限約 480 GB（11/13 一位 512GB 使用者的 oMLX log，Apple 沒有文件），比舊的 75% 高很多。還是建議明確設定成同樣的值（480 GiB，留 32 GiB 給 macOS）。不要設 483328，會比預設低。oMLX #5165（沒設時卸載模型會把上限重設成 0）已在 0.8.0 修好，明確設定的理由是 #4040：沒設時閒置約 2 秒後第一個 forward 卡約 900 ms。

sudo sysctl iogpu.wired_limit_mb=491520

這個設定重開機就會消失，要寫成 LaunchDaemon。另外 GPU 閒置約 2 秒後 macOS 會把 wired 記憶體收回，下一個請求會多等 0.3–2 秒；可以設 iogpu.disable_wired_collector=1，或用 MLX 0.32.4 以上的 MLX_METAL_RESIDENCY_REFRESH_INTERVAL_MS。oMLX 0.8.0 另有 Keep GPU Awake After Requests（預設 5 分鐘，可調長）。

速度怎麼估

Decode 受頻寬限制：每產生一個 token 都要把 active 權重讀一遍，所以大約是「有效頻寬 ÷ 每 token 讀取量」。但大型 MoE 在 M5 Ultra 上的有效頻寬只有規格的 25–40%（GLM-5.3-Flash 18B active 只跑到 31–41 tok/s），用理論值會高估太多。所以這頁的推估是拿 M3 Ultra 的實測乘上上表的世代倍率；M5 Ultra 256GB 的實測直接沿用（頻寬一樣）。兩者對不上時取保守值，並在備註寫明。Prefill 受算力限制，bit 數影響很小（4-bit 到 8-bit 只差 0–14%）；decode 的話 8-bit 比 4-bit 慢約 20–25%。

主力候選

11/26 起先用benchmark 門檻篩過，主力候選只剩兩個：DeepSeek V4.1 Flash 1017 和 MiniMax M3.1 Flash。兩個都是 MoE，官方權重本身就是低 bit（MXFP4、NVFP4 experts），原精度就放得進 512GB。差別在 KV 大小、prefill 速度和工具鏈成熟度。GLM-5.3-Flash 和 Qwen3.8-Flash-Next 的 DeepSWE 不到 70，移出主力；它們的數字和還能做什麼，見下一節。

表裡的分數都是各家自己公布的，跑分環境不一定一樣，只能看大概，空白代表官方沒有公布這一項。第三方的分數見下一節：Vals 的 Terminal-Bench 4.0 DeepSeek 31.8、MiniMax 25.3（都用 mini-swe-agent），tbench.ai 的 Terminal-Bench 4.1 DeepSeek 38.5（Claude Code harness），MiniMax 沒有。

Benchmark 門檻

這頁的主要用途是 Claude Code 這類長時程、改很多檔案的 coding agent，所以用 DeepSWE v1.1 當主要的尺。它是 Datacurve 做的 113 題軟體工程任務（91 個 repo、5 種語言），題目從頭寫起避免訓練資料污染，verifier 看行為、不看實作。問題是它沒有一個涵蓋這些開放模型的獨立榜：Datacurve 官方榜停在 9/22，Mercor 只重跑了幾個；Epoch AI 評它「Flawed」，113 題裡至少 23 題會把對的解判成錯；別家重跑同一個模型會差 3–6 分，95% 信賴區間約 ±6–7。所以門檻只做粗篩，再加一把第三方的尺，專門抓「自報很高、換一把尺就掉到三分之一」的模型 社群回報。

    DeepSWE 自報多半用 mini-swe-agent，但版本從 2.4.2 到 2.4.6 不等；Qwen 是 Claude Code 和 mini-swe-agent 兩種 harness 取高；Mistral、MiMo、Beam、Muse 沒寫 harness。Mercor 的 DeepSeek 沒標是不是 1017 版。Vals 的 Terminal-Bench 4.0 全部用 mini-swe-agent，是同一把尺；tbench.ai 的 Terminal-Bench 4.1 由各家自選 harness 和 effort，括號裡是 harness。Vals Index 是 11/21 的 v2.2，每個模型都比 11/19 低 1.5–2.4 分（原因不明），Hy4 對 DeepSeek 從 59.4 對 61.3 變成 57.9 對 59.7。70 和 20 這兩條線都在誤差範圍附近，MiMo、Sage 的 67.9 只差 2 分；之後新模型的自報分數落在 68–72 時，要等第三方數字再判斷。研究筆記在 research_notes/2026-11-26 全面更新/inkling_and_benchmark_gate.md。

    Inkling 系列：Small 放得下，但不列入

    Thinking Machines 公開權重的有五個：Inkling（975B／41B active，官方 NVFP4 就有 551 GiB，放不下）、Inkling-Small（276B／12B，7 月，已被下一代取代）、Inkling 2 Small（594B／17B，11/12）、Inkling 2 Mini（26.4B／3.4B，11/20）和一個研究用的 varloop 版，都是 Apache-2.0，沒有更大的 Inkling 2 已確認。Inkling 2 Mini 是給 32GB 機器的，評估見 M1 Pro 32GB 分頁。

    Inkling 2 Small 的官方 NVFP4（366.5 GiB）加原生 1M 的 KV（只有 8 層 global attention，含 drafter 每 token 36 KiB，1M 約 36 GiB）再加 32 GiB prompt cache，約 441 GiB，放得進 480 GiB，但要 oMLX 0.8.3 以上：0.8.2 以前 sliding window 層的 KV 不截斷，1M 會多約 160 GiB 推估。11/23–11/24 M5 Ultra 512GB 第一次有實測（oQ4e、MTP 開，oMLX 0.8.2／0.8.3）：prefill 32K 1,310、128K 824（首 token 159 秒）、200K 545（365 秒），decode 41–54 社群回報。prefill 只有 DeepSeek 的 1/3 到 1/7，每個長度都比 GLM 慢；照這個趨勢，冷的 1M prompt 要約 2 小時 推估。分數也撐不住：自報 DeepSWE 72.1，但兩個第三方的 Terminal-Bench 都只有 12–13，約 DeepSeek 的三分之一。它的強項是長文件（LongBench v2 70.6，DeepSeek 69.0），只有之後放寬「一次只常駐一個模型」、要一個看長文件的第二模型時才有角色。從觀察名單拿掉。

    GLM 和 Qwen 還能做什麼

    GLM-5.3-Flash 是最可惜的一個。三個來源的 DeepSWE 都落在 63–64，比 DeepSeek 低 7–14 分；但 Terminal-Bench 兩個榜都跟 DeepSeek 差不多（tbench.ai 用 Claude Code harness 37.0 對 38.5，Vals 37.4 對 31.8），工具鏈也最齊（oMLX、llama.cpp、mlx-vlm、ds4 都能跑），8-bit（343 GB）加 1M context 放得下。DeepSeek 和 MiniMax 的 runtime 都出問題時，它是第一個備援。512GB 的社群上傳：官方 FP8／社群 oQ8e prefill 1,950–2,090、decode 40–55 社群回報。

    Qwen3.8-Flash-Next 在這頁的角色本來就是「最快讀完大量文件」，不是寫程式。DeepSWE 58.7（Tencent 重跑 65.1），也沒有第三方的 agentic 數字。8-bit oQ8e-mtp（195 GB）128K prefill 4,855–4,914，仍是最快的 社群回報；原生 context 只有 262K，授權是 qwen-community-1.0。只要快速讀過大量文件、不改程式時再拿出來。

    兩個的量化和速度明細在 11/26 以前的版本裡（GitHub Pages repo 的歷史）。

    其他看過、沒列進表的：Recursive Flint（40B，太小）、Ripple-65B Preview（65B dense，DeepSWE 44.3）、Kimi-K3.1-Pro（2.78T）和 LongCat-2.5（1.78T）放不下、Kimi K3（2.8T，放不下；Mercor DeepSWE 72.9）。11/21–11/26 新出的：China Telecom Xing4.1-Preview（285B／17B，自報 Terminal-Bench 4.0 28.7，比 DeepSeek 弱，Mac 上沒有 runtime）、inclusionAI Ling-3.2-air（124B／5.5B，沒有 coding 分數，重點在工作流程和文件）。Hy4 和 Hy4-flash 的細節：Hy4 官方 FP8 786 GB 放不下，512GB 上只能跑 oMLX 的 oQ4h（452 GB，約 4.6 bit，沒有 KL）；KV 每 token 約 93 KiB，256K 時 prompt cache 只剩約 25–30 GiB，1M 放不下 推估；M5 Ultra 512GB 4K prompt 的 prefill 654、decode 20 tok/s 社群回報。ERNIE 5.5 Flash Preview（280B／14B，Apache-2.0）是唯一一個 coding 分數接近 DeepSeek 的新模型：自報 Terminal-Bench 4.0 46.5、DeepSWE 71.2，官方預設檔 165.9 GB（routed experts 是 MXFP4 的 W4A8 QAT）。但 oMLX、mlx-vlm 的支援 PR 11/24 沒合併就關了，PR 裡 M5 Ultra 512GB 不開 draft 的 4.1K prompt 是 prefill 約 1,200、decode 約 16 tok/s 社群回報；等有 Mac runtime 和第三方分數再看。

    量化

    原則

    1. 官方已經是低 bit 的權重，不要重新量化。 DeepSeek 的 MXFP4 experts 和 FP8 Engram、GLM 的 FP8、MiniMax M3.1 的 NVFP4（QAT 訓練出來的）原樣保留就好。DeepSeek V4 重新量化 experts 之後，KLD 從 0.010 變成 0.029。
    2. 低 bit 只用在 routed experts。 Attention、線性注意力和 SSM 狀態、DSA indexer、shared experts、embedding、lm_head 都維持 8-bit，router 用 8-bit 或 BF16。Routed experts 佔參數的 95–98%，而且最不敏感。
    3. 放得下就選高 bit。 在 M5 上，prefill 幾乎不受 bit 數影響，MoE 的 decode 8-bit 也只比 4-bit 慢 20–25%。
    4. 不要用 uniform 4-bit。 新架構在 uniform 4-bit 下可能崩掉：Qwen3.8-Flash-Next 的 PPL 會多 20.6%，用敏感度混合的版本只多 1.3%。Experts 低於約 3 bpw 就會開始斷崖式下降。

    格式怎麼選

    • MLX：自己做 PTQ 用 affine（group 64），來源本來就是 MXFP4 才用 mxfp4。mlx-lm 的 nvfp4 不會設 global_scale，品質比 affine 差，不要用。mxfp8 在 M5 上沒有算力優勢。
    • oMLX oQ（oQ4e／oQ6e／oQ8e）：依敏感度分配 bit 數，「e」代表用 imatrix 做 rounding，會保留原生 FP8／MXFP8 tensor。這幾個模型目前最實用的 MLX 量化。
    • GGUF：Unsloth 的 UD-*_K_XL 有公開 KLD 表，最好比較。但 DeepSeek 的 UD-Q3_K_XL 以上把 Engram 存成非官方的 MXFP8，主線讀不了，見Unsloth Dynamic v3.1。IQ 系列 decode 比 K-quant 慢 5–10%；NVFP4 在 Metal 上沒有 mul_mat，會退回 CPU。
    • KV cache：維持 BF16。MiniMax M3.1 的 KV 最大（1M 要 135 GiB），但官方權重只有 252 GB，BF16 也放得下。oMLX 0.7.1 新增 Affine4／Affine8 KV（full-attention 的 KV 省 74%／49%，prefill 慢約 4%），只有記憶體不夠時才需要。mlx-lm 的 --kv-bits 會靜默跳過 MLA、線性注意力的 cache。

    各模型的量化選項

    Unsloth Dynamic v3.1

    Unsloth 10 月 30 日公告 DeepSeek V4.1 Flash 1017 的 GGUF 改用 Dynamic v3.1（標成 preview），宣傳「64GB+ RAM 就能跑」。實際上換新的只有 2-bit 以下的檔：10/28 重新上傳 UD-IQ1_S、UD-IQ1_M、UD-Q2_K_XL；UD-IQ2_XXS 也傳過，但 10/29 又換回 10/19 的原檔。UD-IQ3_XXS 以上，包括這頁用到的 UD-Q4_K_XL 和 UD-Q8_K_XL，從 10/19 起一個 byte 都沒變，Unsloth 的 Daniel Han 也說 Q3_K_XL 以上不需要更新。Unsloth 沒有公開 v3.1 改了什麼方法，到 11/19 也沒有任何第三方用 v3.1 的檔做過評測，UD-Q4_K_XL 和 UD-Q8_K_XL 也沒有重傳。Unsloth 11/13 的 Engram README 自己寫明主線 b12233 起會把 MXFP8 表讀錯。對這台 512GB 來說，結論不變：繼續用 oMLX＋oQ4e-ngram-mtp。

    平均分追上 Q8，逐 token 差很多

    Unsloth 自己的六項評測（AIME25、GPQA-D、LiveCodeBench v6 等），v3.1 的 UD-Q2_K_XL 平均 87.49，只比 UD-Q8_K_XL 的 87.68 低 0.2 分。但它跟原模型逐 token 的 top-1 一致率只有 91.5%（Q8 是 98.5%），大約每 12 個 token 就有一個選得不一樣，答案被截斷的比例也從 1.48% 升到 2.10%。單題 benchmark 是一次問答，Claude Code 要連續幾十輪呼叫工具，偏離會累積，平均分看不出來。11/2 Unsloth 自己補了一輪：agentic 評測用 512K context，加了 DeepSWE 1.1、Terminal-Bench 2.1、AutomationBench，宣稱 1-bit 版 DeepSWE 68.1。但只有 Unsloth 自己跑，每個量化的 agentic 分數只畫在圖上，UD-Q3_K_XL 以上沒有任何 benchmark 數字，方法也沒公開；社群也有人指出這兩個 benchmark 業界已經不太用了。另外，文件的 KLD 文字表從 10/26 到 10/30 沒改過，2-bit 以下那幾列還是舊檔的數字，v3.1 的 KLD 只畫在圖上。

    「64GB 能跑」沒有附任何量測

    速度

    兩張圖都是兩個主力候選的建議配置。DeepSeek 的 prefill 和 decode 用 11/13 起 512GB 的社群上傳（看得到 CED、A8，仍未驗證，見下面的說明）；MiniMax 是推估，512GB 上到 11/26 還沒有任何上傳。移出主力的 GLM 8-bit（prefill 1,950–2,090、decode 40–55）、Qwen oQ8e（A8 關的 128K 4,855–4,914）和 Inkling 2 Small 也都是 512GB 的社群上傳，留在下面的其他實測。其餘實測來自 MacStories 在 M5 Ultra 256GB 上用 oMLX 0.7.0.dev2 的測試，推估的換算方式見前提。

    Prompt cache 比 prefill 速度更重要。 同一個 256K prompt，Qwen3.8-Flash-Next 在 M5 Ultra 上冷啟動要 104 秒，cache 命中後只要 5.8 秒。Coding agent 每一輪都會重送幾乎一樣的 prefix，所以 server 能不能穩定命中 cache、cache 能不能放到 SSD，影響比 prefill 快兩倍還大。

    oMLX 0.7.2 剛修好一個 Claude Code 專屬的問題：工具結果後面附的 hook、rule、reminder，以前會被搬進最前面的 system block，所以每一輪都重算整段對話（#4712）。另外 DeepSeek 開 SSD cache 時以 8,192 token 為一個 block，最後 8K 以內有變動就要從那個 block 的開頭重算。一般往後追加的回合不受影響，分支或改到最後 8K 內的內容才會重算，在 M5 Ultra 上最多約 4–5 秒。DeepSeek 線上是 128 token 一個 block（見 DeepInfer）。

    DeepSeek 的 prefill 以打開 CED 為前提，11/26 改成 3,000–4,050 tok/s（社群回報）。11/21–11/25 又有 7 個正式版（0.8.0–0.8.3）、CED 開、A8 關的 session，32K–195K 仍分快的 3,680–4,060、慢的 3,150–3,335 兩群，0.8.0 和 0.8.2 都有慢的，Engram 放 SSD 或 RAM 也都有，所以不是版本或配置的問題；上限從 3,900 提到 4,050，下限不變，仍沒有 256K 以上的上傳。以下是 11/19 時的說明：512GB 的社群上傳（11/13–11/14，跟這頁的配置相同：Engram 放 SSD、CED 開、A8 關，oMLX 0.7.4.dev1／0.8.0rc1，temperature 1，6 個 session）32K–195K 是 3,525–3,995；另一位上傳者（含唯一一筆 0.8.0 正式版）只有 3,009–3,180，原因不明，所以取 3,000–3,900。Engram 放 RAM 的多數上傳也一樣，跟官方 oQ2e 的 3,735–3,958（M5 Ultra 256GB，0.8.0，#5376）一致。開 MTP 的 decode 取 60–90，不開 speculative 取 46–52。沒開 CED 只有 1,243–2,406。A8 prefill（INT8 activation）不要開：0.7.3 的 A8 不涵蓋 oQ4e 的 MXFP4 experts（要 0.7.4.dev1 的 #5058），維護者自己說 A8 是 lossy，#5108 也回報 A8 和 CED 一起開時出現 thinking 迴圈、M5 Ultra 當機。0.8.0 正式版 A8 預設關閉，標「May reduce quality」。A8 開在 32K 以上只多 10–13%，不採用。

    Speculative decoding

    MoE 做 speculative decoding 的效益比 dense 模型小很多：驗證 k 個 draft token 時，每個 token 都會選到不同的 experts，讀取量幾乎跟 token 數成正比。TensorFold 量到驗證 4 個 token 要讀約兩倍的資料。實際上只有附專用驗證 kernel 的 engine 才有明顯加速，而且一般的寫法常常反而變慢。

    TensorFold 是什麼

    是一個 inference engine，不是新的演算法。用 Zig 加自己寫的 Metal kernel，把內建 MTP、DFlash／DFlash2 和「recall」（從先前請求複製 draft）包在一起，而且會逐 byte 檢查輸出跟不開 draft 時完全一樣，所以是 lossless。它在 M5 上會用 GPU 的 tensor 單元驗證 draft tree。Qwen3.8-Flash-Next 6-bit 加 MTP 已經在單台 M5 Ultra 上驗證過；MiniMax 10/31 起支援（#1235），但用的是社群的有損 checkpoint（KL 0.244–0.295），不是官方權重。GLM-5.3-Flash 官方仍寫單機沒有驗證、要兩台 M5 Ultra，但 11/10 有人在單台 M5 Ultra 512GB 用 1.2.5 跑起它自己的 4-bit（182 GB），32K prompt decode 89.2、prefill 2,088 tok/s，比同機 oMLX 跑 oQ6e 的 58.1 快，代價是精度低兩級。官方數字漂亮，但唯一一份獨立測試修正 thinking 設定之後，加速大概打平。最新版是 1.3.5（11/25）：1.3.0 的 DeepSeek prompt attention kernel 約快 1.5 倍（#3351）；1.3.2 在 M5 Ultra 上讓 DeepSeek 1–2 個 stream 的 decode 快 6–17%，單 stream 不開 draft 46.4–49.5、greedy 82.2–84.3 tok/s，輸出逐 token 不變；1.3.3–1.3.5 加了 DeepSeek 多 stream decode 合併 dispatch（#2954）、DSpark 在 GPU 上選 draft（#3405）、冷 prompt 預讀 Engram（#3459），以及自家的 TFQ3 量化格式。#3547 用 11/24 的 main 在 M5 Ultra 512GB 量官方 FP8、不開 draft：decode 4K 50.4、32K 48.3，32K prompt 1,505–1,512 tok/s，比 1.2.10 的 30K 1,064 快約四成，但仍不到 oMLX 開 CED 的一半 社群回報。同一份測試確認 1.3.2 起預設的 Metal 4 路徑沒有 decode 停頓。#1720 在 11/13 合併，1.2.8 起以實驗功能提供（要設 TF_EXPERIMENTAL=deepseek）。1.2.10 在 M5 Ultra 512GB：16 個 prompt 的 DSpark greedy 89.3、sampled 72.7、不開 draft 51.5；冷 prompt 2K 631、8K 917、30K 1,064 tok/s，開不開 draft 輸出的 token hash 都相同（見速度的表）。decode 跟 oMLX 的社群上傳差不多，prefill 比 oMLX 開 CED 慢很多，不影響推薦。11/11 X 上流傳的「Qwen3.8-27B 單張 RTX 5090 破 1,000 tok/s」是另一個 engine（Cinference）把 8 條平行 lane 的速度加總，作者自己說實際使用約 350；TensorFold 同一天的 fanout 模式也是多 lane 加總（8 條瞬間最高約 926），還沒進 repo。27B 不是這頁追蹤的模型，也不能跟主力模型同時常駐。

    Fireworks 的 1,500 tok/s

    Fireworks 10 月 21 日在 X 上公布，DeepSeek V4.1 Flash 1017 在它的 Ultrafast 模式跑到 1,521 tok/s。文件的寫法是「agentic coding 任務的輸出速度目標 1500+ tok/s」，並說是同一個模型、品質不變。Ultra-fast 11/3 起是 serverless preview，用 router ID 就能呼叫，每百萬 token 輸入 $2.40、cache 命中 $0.048、輸出 $9.60（一般模式的 8 倍），rate limit 較低。Fireworks 沒說用了什麼硬體和方法。Artificial Analysis 11/19 的 5 天平均：Ultra-fast 726 tok/s、Fireworks 一般模式 235、Baseten FAST 895、DeepSeek 自己的 API 172。第三方量到的不到宣稱的一半。

    大概是怎麼做的

    • 一定是靠 speculative decoding。 每產生一個 token 要讀約 10 GB 的 active 權重，不用 speculative 要 15 TB/s，單張 GB300 只有 8 TB/s。而且 batch 1 卡在每層的延遲，不是頻寬。
    • 公開資料裡最接近的是 SGLang。 4 張 GB300、batch 1：光是 kernel fusion 就從 35 提到 203 tok/s，加上 DSpark 到 558，再做 fusion 和 4 路 tensor parallel 到 874（平均每步接受 5.5 個 token，但是用 temperature 0 加隨機 token 測的，接受率偏高）。
    • 要到 1,521，每一步要比 SGLang 快約 1.8 倍，或是 draft 比 DSpark 的上限 6 個 token 更長。 比較可能的組合是多張 Blackwell 在同一個 NVLink 網域內做 tensor parallel、FP4 權重和 KV、刻意壓低 batch，再疊上 n-gram 這類長 draft。Coding agent 的輸出大量照抄 context，長 draft 很容易被接受，這也說明它為什麼只標榜「agentic coding」。這一段是推論，Fireworks 沒有證實。
    • DeepSeek 自己線上的數字也支持這個推論。 DeepInfer 的文件寫，線上的 DSpark 一次 draft 5 個 token，真實流量平均每步只接受 3.2–3.3 個。每張 GPU 同時跑約 60 個序列、每張每秒約 14,500 token，換算每個使用者約 240 tok/s，跟 Artificial Analysis 量到的 178–204 tok/s 對得上。光靠 DSpark 到不了 1,521。

    哪些能用在 M5 Ultra

    • 能用：DSpark（已經在用）；fused kernel（oMLX 0.7.1 做的就是這個，M3 Ultra 上 decode 從 20.9 提到 34.3）；非 thinking 模式寫程式時用低 temperature 提高接受率（thinking 模式官方固定 temperature 1.0，不要改）；改檔、重寫檔案的回合疊 n-gram draft（llama.cpp 的 ngram-mod，能不能和 DSpark 一起開要看 engine）。
    • 不能用：多 GPU 的 tensor parallel、合計 32 TB/s 的 HBM，以及讓一次驗證 6 個 token 幾乎不花成本的 FP4 tensor core。
    • 本機的上限：1.2 TB/s ÷ 每 token 約 10 GB，不開 speculative 的理論上限約 120 tok/s。就算每步都接受 6 個 token，1,500 tok/s 也要每秒跑 250 步，至少要 2.5 TB/s（MoE 驗證多個 token 要讀的 experts 還更多）。本機合理的目標是這頁的 60–90 tok/s。

    要拿 Fireworks 當雲端備援的話，它有 Anthropic Messages 相容端點，Claude Code 換 base URL 就能用，count_tokens 回 404（Claude Code 會退回字數估算），prompt cache 是自動的、不看 cache_control，要用 ANTHROPIC_AUTH_TOKEN 帶金鑰。見混合部署。

    DeepInfer

    DeepSeek 10 月 20 日開源了 DeepInfer，也就是它自己線上跑 DeepSeek V4.1 Flash 的推理框架（Apache-2.0，以 vLLM 為基礎）。目前只支援 V4.1 Flash，硬體只有 NVIDIA SM100 和華為 Ascend 950，11/18 的 nv-dev 分支加了 SM120（8× RTX PRO 6000），開源的部分只有 offline inference。KV cache 系統和負載平衡跟內部基礎設施綁在一起，沒有開源，但部署 Q&A 文件把設計和參數寫得很詳細。同時開源的 deepseek-recipe（MIT）負責 API 請求和 token 之間的轉換，行為跟官方 API 一致。DeepInfer 本身不能在 Mac 上跑，但下面這些做法和數字可以直接拿來用。

    CED 是什麼

    公開的 1017 權重是 causal encoder–decoder（CED）結構：40 層裡前 20 層是 encoder，後 20 層是 decoder。Decoder 的全域 KV 由第 20 層從 encoder 的輸出投影出來，不需要 decoder 自己算；decoder 每層另外只有一個 128 token 的滑動窗。所以 prefill 時 decoder 只要處理最後一小段，就能接著 decode。DeepInfer 把這個做法叫「decoder SWA bounded replay」，線上只重算最後 140 個 token（128 的窗口加上 speculative 回退需要的長度），整體 prefill 計算量幾乎減半。重算那一段開頭的 token 看到的窗口會被截短，所以是近似算法，但 DeepSeek 線上就是這樣跑。

    Mac 上誰有實作

    oMLX 9 月就合併了（PR #3607），tail 長度 128。0.7.3 預設關閉，0.8.0 正式版起預設開（A8 預設關）。PR 在 M3 Ultra 量到 21K prompt 的冷 prefill 從 430 變成 700 tok/s（+63%），oMLX 介面上的說明則寫 +74–79%；DSpark 的接受率不受影響。這頁 DeepSeek 的 prefill 用的是 512GB 上開了 CED 的社群上傳。ds4 也會跳過 decoder，但改成精確重建最後 2,541 個 token，結果跟完整計算相同。

    混合部署

    Strata 是什麼

    指的應該是 Niko1221/Strata：一個把 MoE experts 分層放在 GPU 記憶體、RAM、SSD 的 engine（MIT，10/29 出 0.2.8），支援 Qwen3.8-Flash-Next、DeepSeek V4.1 Flash 1017 和 Qwen3.6-35B-A3B，不支援 GLM 和 MiniMax。Mac 版的 Qwen 從 10 月 13 日起是實驗性的 Metal engine，只有 experts 超過 Metal 可用記憶體的 60% 才會開始從 SSD 串流。Qwen3.8-Flash-Next 連 BF16 都只要 360 GB，在 512GB 上分層根本不會啟動，Strata 就只是另一個單模型的 Metal engine。0.2.7.1 新增的 Mac 版 DeepSeek 只提供 2.00／2.25 bpw，這兩組是 ISTA 的 GSQ-RCO 量化，不是 Unsloth 的（KL 0.170／0.107，PPL 比原模型高 15.5%／7.3%）。每個 token 從 SSD 讀 48–111 MB，DSpark 關閉，只在 M5 Max 128GB 上測過：32K prompt 609–720 tok/s，0.2.8 修好記憶體洩漏後 decode 穩定在 18–22 tok/s。它是給放不下模型的小記憶體 Mac 用的，512GB 放得下官方精度的 oQ4e，用不到。另外有一篇同名論文（OSDI ’26）講 GPU／CPU 間的 KV 分層快取，只支援 NVIDIA。

    M1 Mac mini 適合做什麼

    這台 M1（16GB、頻寬 68 GB/s、沒有 Thunderbolt 5）不適合加入推論：頻寬只有 M5 Ultra 的 1/18，也不能用 RDMA。比較適合做 RAG 的周邊工作，例如文件轉文字和 OCR、跑小的 embedding 與 reranker、向量資料庫，或 LiteLLM 這類 API gateway，讓 M5 Ultra 的記憶體全部留給主力模型。11/12 起分工改成：批次的 OCR、文件解析、embedding 和 rerank 交給手上那台 RTX 3060 Ti 小機殼（llama.cpp 7B 基準 prefill 2,991 tok/s，M1 只有 118），M1 只放向量資料庫和 gateway，見3060 Ti 小機殼分頁。

    到貨後的步驟

    1. 設定記憶體上限。 先看預設值：sysctl iogpu.wired_limit_mb 和 Metal 的 recommendedMaxWorkingSetSize。macOS 27.2 上 512GB 的預設 Metal 上限約 480 GB（11/13 一位 512GB 使用者的 oMLX log；改設 491520 跟不設沒差）。所以不要設 483328，改成確認預設值後明確設成同樣的值（例如 491520，480 GiB）寫進 LaunchDaemon。#5165（卸載模型把上限重設成 0）已在 oMLX 0.8.0 修好；明確設定的理由是 #4040：沒設時閒置約 2 秒後第一個 forward 卡約 900 ms。oQ4e-mtp 放 RAM 的峰值到 408 GB，上限要高於這個值。oMLX 0.8.0 的 Keep GPU Awake After Requests（預設 5 分鐘，可調長）處理閒置後收回 wired 記憶體，coding agent 兩次請求可能超過 5 分鐘，建議調長。另外在 omlx serve 的環境設 MLX_METAL_RESIDENCY_REFRESH_INTERVAL_MS=1000：256GB 的機器上有三位使用者靠它避開閒置後重新 wire 時的 watchdog panic（#4981），512GB 還沒人測。macOS 27.3 beta 2（11/16）也沒提 wired limit。台灣訂單大約 2027 年 1 月才到，到時再查一次最新版本。
    2. 確認 Neural Accelerator 有在用。 MLX 0.32.4 以上（11/25 出了 0.32.5，多了一批 M5 的 NAX kernel，oMLX 下一版才會帶）；llama.cpp b10733 以上而且 log 出現 has tensor = true。不要拿 LM Studio 內建的 llama.cpp 當基準。
    3. 規劃 2TB SSD。 兩個主力候選：DeepSeek oQ4e-ngram-mtp 512 GB、MiniMax 官方權重 252 GB，合計約 764 GB，再加 SSD prompt cache 100–200 GB。要留 GLM-5.3-Flash 8-bit 當備援的話再加約 343 GB（社群現成的 oQ8e-mtp 342.2 GB，或 mlx-community 11/22 的 oQ8-mtp，都沒有 KLD），合計約 1,300 GB 還放得下。不要在本機留 BF16／FP8 原始檔；GLM 若要自己轉 8-bit，轉換時會同時佔 328＋343 GB，轉完就刪原檔。要拿 Unsloth 的 UD-Q8_K_XL 當精度對照的話，SSD 再多 508 GB，2TB 會放不下，用外接碟或做完就刪。冷備份放外接 Thunderbolt 5 SSD，但不要直接從外接碟讀。
    4. 裝 oMLX 到貨時的最新正式版（至少 0.8.3），先跑主力配置。 0.8.3 起 DeepSeek 的 Lightning MTP 預設深度是 5，以前手動存成 3 的會變回 Model default。 DeepSeek oQ4e-ngram-mtp、Engram SSD offload、DSpark，prompt cache 熱層調到 64 GiB，SSD 層放內建 SSD。CED 0.8.0 起預設開，載入時 log 仍要出現 CED prefill enabled: decoder tail 128。A8 prefill（a8_prefill_enabled）維持關閉，只拿來做開、關對照；只有在 0.7.4.dev1 手動存過 A8 開的模型會保留，要改回。Advanced 的 Keep GPU Awake After Requests 調長（預設 5 分鐘）。不要開 MoE expert offload，會停用 DSpark。
    5. 用自己的 agent trace 量測。 在 4K、64K、256K、1M 下量 prefill、decode、cache 命中率和峰值記憶體。每次 A/B 都在同一個 engine 裡開關 speculative decoding，thinking 設定一致，以 temperature 1 為準、0 當對照。DeepSeek 的 prefill 在 CED 開、關各量一次。連續跑冷的長 prompt 時 GPU 會降頻（oMLX #5121 在 M3 Ultra 上 prefill 最多掉 65%；回報者已確認是 GPU 超過 80–82 °C 降頻，風扇固定 3,200 rpm 以上就不掉），量測時把風扇固定在最高轉速，或每輪之間讓機器降溫。另一種情況不是過熱：TensorFold #1720 的測試者在 M5 Ultra 512GB 上跑了約半小時後，GPU 滿載但時脈很低，速度掉到三分之一，持續三小時，thermal pressure 一直是 nominal，重開機才恢復，原因不明。每輪量測前先跑一格固定的對照，數字掉了就重開機再量。
    6. 換第二候選跑同一組 trace。 MiniMax M3.1 Flash 官方權重跑一次；時間夠的話也跑備援的 GLM-5.3-Flash 8-bit（在 512GB 上已有人用 recipe 版 oMLX 跑到 1.04M、峰值約 263 GB 沒有 OOM，用正式版再確認一次）。DeepSeek 也用 ds4（main，#1073 已在 11/2 合併；ds4 沒有 release）跑一次 MXFP4 GGUF 對照，中文文件要注意 #1255 的 tokenizer 差異（修正 #1346 未合併）。
    7. 檢查長 context 的正確性。 在 256K 和 1M 做 needle／多文件檢索，對照官方 API 的答案。
    8. 接 Claude Code。 透過 Anthropic Messages API 接 oMLX，看每一輪的 prefix 是否 byte 一致、cache 命中率多少；DeepSeek 再跟 ds4 的 DSML 重播比較。把幾個 Claude Code 請求錄下來，用 deepseek-recipe 轉成 token ID，跟 oMLX 實際送進模型的比對。再讓它讀一個含 <｜DSML｜ 字串的檔案，確認不會被當成工具呼叫。Claude Code 用 2.1.328 以上；2.1.330（11/20）修了很長的對話壓縮之後卡住幾分鐘的問題，2.1.331（11/23）起自訂 endpoint 回沒有名稱的 tool call 不再當掉、改成報錯繼續，2.1.332（11/25）起自動壓縮連續失敗後會在 context 上限再壓一次。2.1.332 起 Desktop app 的 Code 分頁會忽略不是 claude 開頭的模型 ID，接本機 server 用 CLI。oMLX 0.8.3 起 Claude Code 的 WebSearch 工具可以在本機模型上用（#5342）。v2.1.323 起不認得的 model ID 一律當 1M context；v2.1.325 起 CLAUDE_CODE_MAX_CONTEXT_TOKENS 對所有不認得的模型 ID 都生效（包括 claude- 開頭的）。兩個主力候選都是原生 1M，CLAUDE_CODE_MAX_CONTEXT_TOKENS 設成 oMLX 實際設定的 context；換成原生 262K 的模型（例如 Qwen）時要跟著改。其他模型也建議先用 /autocompact 設一個較小的壓縮點。oMLX 在 prefill 期間每 10 秒送 ping，但 Claude Code 對只有 ping 的串流大約 10 分鐘就會中止；CED 沒開的冷 1M prompt 會超過，會斷的話設 CLAUDE_STREAM_IDLE_TIMEOUT_MS=1800000（自訂 base URL 要 2.1.328 起才有效）。oMLX 有 count_tokens，/context 的數字是準的。從 oMLX 0.8.1 啟動 Claude Code 時會設 CLAUDE_CODE_AUTO_MODE_SERVER=0，auto mode 才能用在本機模型上（#5409）；自己設 base URL 的話要自己加。再刻意讓一次工具呼叫失敗，看模型會不會進入重試迴圈；0.8.1 起 DeepSeek 寫壞的工具呼叫會回 invalid_tool_call（#5416），看 Claude Code 怎麼處理。
    9. MiniMax M3.1 Flash 用 oMLX 正式版跑。 權重 10/23 已釋出、數字已經用 config.json 重算過。0.7.3 正式版（10/31）已含 PR #4777，用官方權重開 1M context 跑第 5 步的 trace。0.8.0 正式版已含 MiniMax 在 M5 上的 prefill 加速（#5084、#5157，M5 Max 切片 64K 的 MoE 層快約 1.75 倍）。M5 Ultra 只有 256GB 的 oQ3e／oQ3.5e 社群上傳（64K 約 830、128K 約 760，0.8.0 以前），官方權重沒有。

    • CED 是近似算法。oMLX 的 tail 是 128，DeepInfer 是 140（多留 speculative 回退的長度）；oMLX 的 PR 說明 DSpark 驗證不會走 CED 這條路。#5155（11/10）在 M3 Ultra 上量了 CED 開對關：4K–128K 的 KL 0.0008–0.0057、top-1 一致率 97.3–100%，比單純把 prefill chunk 從 2,048 改成 8,192 造成的差異（0.004–0.017）還小，也不隨 context 累積；但每種情況只測一個 prompt。到貨後還是要用長 prompt 比較 CED 開、關的輸出。
    • oMLX 把整段 prompt 字串直接 tokenize，檔案或工具結果裡的 DeepSeek 控制 token 字串可能被當成真的控制 token，讓模型誤以為要呼叫工具。還沒實測，見到貨後的第 8 步。Sage S2.1 Flash 的部署指南把同一件事當成必須處理：內容裡的控制 token 字串要當一般文字，否則模型會提前結束，工具呼叫和 reasoning 也會壞掉。
    • DeepSeek 官方 repo 有一份 11/17 的回報：官方 API 接 Copilot agent 時，工具參數名稱偶爾變成中文，失敗後進入刪檔重建的迴圈（單一回報，沒有官方回應）。
    • Engram 放 SSD 對 decode 速度的影響只有間接數據：M5 Max 128GB 重度 offload 時佔 decode 時間約 6%。FP8 的 Engram 每列比 4-bit 大一倍，到貨後要確認沒有變慢。prefill 方面，512GB 上放 SSD（3,776–3,995）和放 RAM（3,811–3,973）差不多；#5190 說的拖慢是 256GB 放不下 Engram。
    • DeepSeek 在 M5 Ultra 上的速度：開 MTP 的 decode 取 60–90，不開 speculative 取 46–52。prefill 改用 512GB 的社群上傳：跟這頁的配置相同（Engram 放 SSD、CED 開、A8 關）32K–195K 是 3,525–3,995；另一位上傳者（含唯一一筆 0.8.0 正式版）只有 3,009–3,180，原因不明，所以取 3,000–3,900。M3 Ultra 換算的方法（×2.3–2.6）對 DeepSeek 已經不適用：M5 專用的 kernel 讓 M5 Ultra 對 M3 Ultra 到約 3–3.7 倍。沒開 CED 只有 1,243–2,406。其他 runtime 的 M5 Ultra 數字都比 oMLX 開 CED 低：llama.cpp pp2048 632，ds4 在 33.5K 是 1,146。

    兩台 M5 Ultra 256GB
    值不值得串聯

    兩台 256GB 加兩條線是 NT$810,180，只比一台 512GB 多 NT$4,780，還多一倍的 GPU 和一顆 SSD。精度不是問題：DeepSeek 和 GLM 8-bit 可以用 oMLX 的實驗性叢集切到兩台，Qwen 單台就放得下。10/31 時擋住這個方案的三個軟體問題，兩個已在 11/18 的 oMLX 0.8.0 正式版修好：叢集的 prompt cache 依餘裕給 2–8 格，DeepSeek 的 tensor parallel 也能跑 CED prefill。剩下的穩定性反而多了新回報：oMLX 的 tensor parallel 在兩台 M5 Ultra 上出現過啟動時 GPU timeout，mlx-serve 的兩台 tensor parallel 卡死後要兩台都重開，TensorFold 的兩台模式在 macOS 27.2 上啟動不了；MLX 的斷線修正仍沒 release，oMLX 0.8.0 也還用不到。第一次有同一個 runtime 的兩台對單台 M5 Ultra 對照（TensorFold 跑 Qwen，社群修正版）：兩台的 decode 只有單台的約 0.9 倍，prefill 約 2.2 倍。11/26 起 Mac 分頁的主力候選先過一道 benchmark 門檻，只剩 DeepSeek 和 MiniMax，兩個都放得進 512GB，叢集最大的好處「放得下」用不到；11/25 又有一位在兩台 256GB 上用 oMLX 0.8.3 跑 DeepSeek，context 過了約 300K 就每輪重算 cache、400K 附近 rank 0 等不到資料逾時。所以建議仍是照原計畫買一台 512GB。以後想加速，oMLX 0.8.0 正式版的 Prefill Accelerator 讓第二台 Mac 只幫忙算 prefill，模型和 cache 都留在 512GB 那台，比組叢集穩。

    建議
    照原計畫買一台 512GB。以後想加速，先考慮 oMLX 的 Prefill Accelerator（0.8.0 起是正式功能，第二台只幫 prefill、不用 RDMA）；真的要組叢集，依每台記憶體切 DeepSeek tensor parallel 的 #5272 已進 0.8.1 正式版（11/21），但只在 M5 Ultra 256GB＋M5 Max 128GB 上跑過
    精度
    DeepSeek oQ4e、GLM 8-bit 用 oMLX 叢集切到兩台；Qwen oQ8e 單台就放得下；MiniMax 官方權重能用 mlx-lm main 或 exo main 切，兩者都沒有 DSpark
    Prompt cache
    oMLX 0.8.0（11/18 正式版）起叢集 RAM cache 依餘裕給 2–8 格（balanced 8 格）；只在單機模擬驗證過，沒有兩台實機的命中率。mlx-serve 的兩台 tensor parallel 有 RAM＋SSD prefix cache。ds4 從 SSD 還原 cache 時，兩台都要重算
    速度
    跟 512GB 開 speculative decoding 的配置比，推估 decode：DeepSeek 0.9–1.1 倍、GLM 1.2–1.35 倍、MiniMax 0.8–0.9 倍、Qwen 不變。只有 64K 以上的冷啟動長文件 prefill 有明顯好處。TensorFold 在兩台 M5 Ultra 上跑 Qwen 的同 runtime 對照，decode 是單台的 0.87–0.91 倍
    怎麼接
    兩條 Apple Thunderbolt 5 Pro 連接線直連；兩台各在系統設定打開「RDMA over Thunderbolt」（macOS 27 起，不用再進 Recovery）；停用 Thunderbolt Bridge，IP 設在 Thunderbolt 埠上。Apple 的 Harbor app 號稱能自動組叢集，但還在 private preview

    DeepSeek 主要走 tensor parallel

    oMLX 0.7.1 讓 DeepSeek V4.1 和 GLM-5.3 可以跨 Mac 跑，0.7.2 再把 DSpark／MTP 帶進叢集，由 rank 0 負責 draft。有人用兩台 M5 Ultra 256GB 開 issue，維護者說每台 256GB 時只有 tensor parallel 的規劃放得下，而且會刻意把 Engram 留在 SSD。這對你沒有損失，512GB 方案本來就這樣放；維護者在兩台 M3 Ultra 上量過，Engram 放不放 SSD 速度差不多，greedy 輸出完全相同。DeepSeek 的 KV 只有一個 head，每台各存一份完整的 KV，但 1M context 也才約 3.1 GiB。11/11 有人在兩台 M5 Ultra 256GB 上用 0.7.4.dev1 跑 oQ4e-ngram-mtp 的 pipeline 也成功（#5178），可能是 0.7.3 的 #4985 把 Engram 算成 SSD 常駐後，pipeline 的規劃也放得下了 推估。

    ds4 是備案：固定兩台 50/50 切的 tensor parallel，V4.1 沒有 pipeline 模式。它的文件前後矛盾，10/5 的版本說 V4.1 在兩台上不支援 speculative decoding，10/10 的 commit 又讓 DSpark 能在 tensor parallel 上跑，這個分頁以較新的為準。11/2 的 commit 讓 ds4 在任一台放不下完整 experts 時維持切分。

    11 月多了兩條路。mlx-serve 11/3 合併兩台 tensor parallel（v26.11.2 進 release），單機有的 DSpark、批次 decode、RAM＋SSD prefix cache 在兩台上都能用，API 有 OpenAI 和 Anthropic 兩種格式。它在兩台 M3 Ultra 上有同一個 build 的單機對照：DSpark decode 56.2 → 88.4 tok/s（1.57 倍），不開 MTP 1.31 倍，8.8K prefill 1,018 → 1,608 實測。兩台 M5 Ultra 在 11/12 的正式對照：plain decode 63.3／62.7 tok/s（2K／32K），32K 首 token 11.5 秒；四台 81.7／79.7。11/20 出了 v26.11.3，release notes 沒提兩台 tensor parallel，#1237 的卡死也還開著 社群回報。exo main 11/1 加了官方精度的 V4.1 1017，tensor 和 pipeline 都能跑，但不載 MTP 層、沒有 DSpark、速度還沒調（兩台 M3 Ultra tensor parallel decode 16.5 tok/s，比單台 18 還慢）。mlx-lm 遇到 Engram 層還是會丟 ValueError。

    MiniMax 是唯一靠兩台省到容量的

    官方權重約 235 GiB，單台 256GB 就算 wired limit 開到 240 GiB，也只剩不到 5 GiB 給 KV，大約 4 萬 token，所以一定要兩台。能切它的只有 mlx-lm main，但 mlx_lm.server 在分散式模式下不接受 draft model，prompt cache 只有 RAM 裡的 LRU，也沒有 /v1/messages，接 Claude Code 要另外架 LiteLLM 這類轉換層 推估。好處是它有 4 個 KV head，tensor parallel 剛好兩台各分一半，1M context 的 135 GiB KV 每台約 67.5 GiB，加上約 117 GiB 權重，仍在 230 GiB 之內。

    oMLX 叢集能不能跑 MiniMax 還沒人驗證過（oMLX 單機的 M3.1 支援 10/31 已進 0.7.3 正式版）。exo main 11/1 加了官方 NVFP4 的 M3.1 Flash，tensor parallel 走 RDMA、pipeline 走 TCP，也有 /v1/messages，但沒有 DSpark、沒進 release（最後一個 release 仍是 4/23 的 v1.0.71）。它在兩台 M3 Ultra 上的 tensor parallel decode 是 19.3–29.4 tok/s（單台 16.6–23.2），對單台的 KL 中位數 4.2e-4 實測。另一條路是 TensorFold：10/31 起能在單台 256GB 上跑 MiniMax，但用的是社群的有損 checkpoint（KL 0.244–0.295），不是原精度。

    oMLX 的叢集文件自己標示「experimental, source-build preview」，Diagnostics 一節也寫「Neither proves the physical Thunderbolt path」。到 11/19 為止，四個模型在兩台 M5 Ultra 上走 RDMA 的公開數字有 TensorFold 的 GLM 4-bit 和 Qwen 6-bit、d-inference 的 GLM 4-bit 等級，以及 mlx-serve 的 DeepSeek 原精度（見速度）；oMLX 叢集在兩台 M5 Ultra 上只有 tool call 的驗證、沒有速度，GLM 8-bit 也只有 oQ8e 跑起來的回報。

    Prompt cache：1 格的限制在 0.8.0 正式版拿掉了

    Mac 分頁自己寫過：同一個 256K prompt，Qwen 冷啟動要 104 秒，cache 命中只要 5.8 秒。所以 cache 能不能穩定命中，比 prefill 快兩倍還重要。單機的 oMLX 有多格 RAM cache 加 SSD 分層，DeepSeek 的配置留了 64 GiB 熱層。0.7.3 以前的叢集模式把 prompt_cache_size 強制設成 1；11/4 的 0.7.4.dev1、11/18 的 0.8.0 正式版改成依每個 stage 的餘裕給 2／4／8 格，餘裕超過 16 GiB 就照 profile（interactive 4、balanced 8、throughput 16）。兩台 256GB 跑 DeepSeek 時每台約用 164 GB，應該落在照 profile 那一級 推估。每個 rank 另外把 cache 快照存到 SSD，預設上限仍是 20 GiB。

    已經有人踩到

    oMLX #3062 用兩台 M4 Max 走 JACCL，發現任何第二個請求（產生標題、摘要、另一個 client）都會把主 session 已經算好的 prefill 擠掉，約 45K token 時每輪要重算 110 秒 實測。Claude Code 剛好會發這類背景請求。換到 M5 Ultra，以 1,000–2,000 tok/s 計算，45K 的 prefix 被擠掉一次要多等 22–45 秒，200K 要 100–200 秒 推估。兩個修正 PR（#3063、#3655）都沒合併就關了，最後是維護者自己在 11/3 用 #5062 修好：除了 1 格的限制，原因還有 tool result 那一輪的 checkpoint 被標成 assistant、會被優先擠掉。修好後五輪 tool loop 第五輪的 cached token 從 743 變 9,266，每輪插一個標題請求也一樣 實測。但這是在一台 M3 Ultra 上模擬 rank server 量的，沒有兩台實機，也沒有 Claude Code 的命中率；byte 上限仍然關閉，8 格長 context 實際吃多少記憶體沒人量過。

    CED 剛接上叢集

    DeepSeek 在 512GB 方案的 prefill 推估是以打開 CED 為前提。10/30 的 #4984 指出叢集的 worker 不讀 per-model settings，CED 和 A8 prefill 在叢集 rank 上都是關的；10/31 合併的 #4985 只修了 Engram SSD offload。11/10 的 #5086 才讓 DeepSeek V4.1 的 tensor parallel rank 跑 CED、A8 和 fused MoE decode，設定跟 Lightning MTP 走同一條路；pipeline 和其他模型不變。11/18 進了 0.8.0 正式版；A8 預設關，要模型自己打開。數字是在 8 層的 checkpoint 上量、再換算成 40 層：M3 Ultra＋M5 Max 走 RDMA，8K prefill 785 → 1,324 tok/s、decode 19.8 → 28.8 實測。#3071（prefixed deployment ID 對不上 per-model settings）11/19 被 bot 以過期關閉，沒有修正，但 #5221 的回報者在 0.8.0rc1 上讀回 rank 的執行紀錄，CED、A8、MTP 的開關都有送到 tensor parallel rank 社群回報。

    可以把 Claude Code 的背景小模型請求導到別的端點（例如 M1 Mac mini 上的小模型），減少被擠掉的次數，但消除不了 推估。512GB 方案本來就沒用到 SpecPrefill、TurboQuant KV、ANE prefill，這幾項在叢集裡被拒絕不算損失。

    Decode：單機越快，增益越小

    拆開 Apple 的表，兩台 tensor parallel 每個 token 的時間約等於「單機時間的一半，再加 5–9 ms 的固定通訊開銷」。單機 20 tok/s 的模型兩台可以到 1.6–1.8 倍，40 tok/s 剩 1.15–1.45 倍，90 tok/s 會落在 0.75–1.1 倍。這四個候選都是 6–23B active 的 MoE，單機本來就快。exo 1.0 在 M3 Ultra 上跑 22B 和 37B active 的 MoE，兩台也只有 1.34 和 1.32 倍 社群回報。

    Prefill：只有冷啟動的長文件受惠

    Pipeline 的 prefill 加速來自把 8,192 token 的 chunk 在兩台之間重疊計算，上限約 2n／(n＋1)：16K 1.33 倍、64K 1.78 倍、256K 1.94 倍。Claude Code 在 cache 命中後每輪通常只新增 1–10K token，兩種切法都只有 1.0–1.3 倍。真正吃得到好處的是 64K–256K 的冷啟動長文件，而且只有能用 pipeline 的 GLM 和 MiniMax；DeepSeek 在 256GB 上主要走 tensor parallel，pipeline 有人跑起但沒有速度 推估。

    兩台各跑不同模型

    精度優先的話，能用的組合是：A 機用單機版 oMLX 常駐 Qwen oQ8e，保留 MTP、n-gram 放 SSD 和多格 prompt cache；B 機跑降精度的 DeepSeek 或 GLM。需要原精度的 DeepSeek 或 GLM 時，再把兩台組回叢集，在 oMLX 裡是部署層級的切換 推估。好處是讀大量文件時兩個模型可以同時開著；壞處是第二個模型永遠是降精度版，組叢集時 Qwen 要先停掉。如果 B 機只是跑 embedding、reranker、向量資料庫，這些本來就規劃給 M1 Mac mini，不值得多買一台 NT$40 萬的機器。

    先買一台 256GB

    NT$402,900 買到的是一台能用原精度跑 Qwen、速度有實測的機器。問題是主力是 DeepSeek（DeepSWE 77.0，Qwen 58.7），單台 256GB 上的 DeepSeek 只剩 Q2 等級。先買一台等於先讓 Qwen 當主力，之後要回到原精度的 DeepSeek 只能補第二台組叢集，而上面的問題全出在叢集上；想改買 512GB 就得先賣掉這台。反過來，先買 512GB 不會關上叢集的門。0.8.0 以前 DeepSeek 的 tensor parallel 只能平均切（512＋256 會被 256 那台卡住容量）；社群 PR #5272（11/20 合併，進了 0.8.1 正式版）讓它依每台記憶體切，照 PR 的做法 512＋256 不會再被卡住，但還沒人在這個組合上跑過。它在 M5 Ultra 256GB＋M5 Max 128GB 上跑起 oQ4e：decode 預設 22–24 tok/s，開 MLX_METAL_FAST_SYNCH=1 後 45–46，再加 MLX_MAX_OPS_PER_BUFFER=64 是 48–52，prefill 1,479–1,907（3.9K–31K）社群回報。#4984 指出的 Engram 常駐排不下的問題，#4985 已在 0.7.3 修好。

    512GB 再加一台，只幫 prefill

    oMLX 0.8.0（11/18 正式版）加入 Prefill Accelerator（#5065，11/4 先進 0.7.4.dev1）：每個 prompt chunk 由輔助機跑前幾層、主機跑其餘的層，兩台交錯同時算，切點依實測速度自動決定。Auto 會在切開反而比較慢時把 prompt 留在主機，兩台要裝同一版 oMLX；輔助機記憶體不足或離線時會自己降層數、重試。模型、KV cache、prefix cache 和 API 都留在主機上，輔助機只放它負責的那幾層。不用 RDMA，Thunderbolt 或 Mac Studio 內建的 10GbE 就夠；輔助機斷線或停掉時，主機從最後一個算完的 chunk 自己接下去。四個候選模型都支援，DeepSeek 的 CED 照常開著。官方實測的主機是 M3 Ultra 512GB，加一台 M5 Max 128GB 後 64K prompt 的 prefill：DeepSeek oQ3e 1,060 → 3,000–3,160 tok/s、GLM oQ4e 540 → 1,390、Qwen oQ4e 1,310 → 3,670、MiniMax oQ4e 300 → 570 實測。M3 Ultra 沒有 Neural Accelerator，主機換成 M5 Ultra 時輔助機的相對速度低很多，加速應該小得多：同樣是 M5 Ultra 的輔助機理論上限約 2 倍，M5 Max 大概 1.3–1.5 倍 推估。這條路避開了叢集的 cache 和斷線問題，但還沒有 M5 Ultra 當主機的數字（11/13 有人在 oMLX 討論區問 M5 Ultra 當輔助機的數字，沒人回）。官方文件建議輸出要跟單機一致時用 Mac 當輔助機。oMLX 11/11 也合併了 Docker 裡的 NVIDIA 輔助機（#5163），等於 PC 也能當 Mac 的 prefill 輔助機，只是官方那張 KL 表就是用 Linux＋NVIDIA 量的（DeepSeek oQ4e 首 token KL 中位數 0.042）。

    怎麼串聯

    線材和接埠

    • 直連，不用 switch。沒有 Thunderbolt 5 switch，RDMA 也不能路由。兩台最少 1 條線就能跑。
    • 建議兩條線。Apple Thunderbolt 5 (USB-C) Pro 連接線 1 公尺（MDW94FE/A），台灣官網每條 NT$2,190。JACCL 會把大訊息分散到所有線上；第二條線只幫長 prompt 的 prefill，不幫 decode。
    • 長度。1 公尺的被動線夠兩台並排或上下疊放；要分開擺才需要 2 公尺的主動線。不要用 TB4、USB4 線，也不要經過 dock。
    • 接埠。每台有 6 個 Thunderbolt 5（背面 4、正面 2）。exo 的文件說 Mac Studio 緊鄰 Ethernet 的那個埠不能跑 RDMA，M5 Ultra 還沒證實，先避開它。
    • 管理網路。兩台背面的 10GbE 接家裡的路由器，SSH、下載模型和 mlx.launch 的 rank 0 位址都走這條，Thunderbolt 線只跑 RDMA 推估。

    最容易出錯的一步

    IP 要設在 Thunderbolt 埠（ibv_devices 列出的 rdma_enX 對應的 enX）上，不能設在 Thunderbolt Bridge 上。oMLX #4720 那位使用者設錯了，oMLX 找不到 RDMA，就默默退回 TCP，decode 只有 16.7 tok/s。接兩條線時 bridge 一定要停用，不然兩端的 bridge0 會形成迴圈，封包無限循環、吃掉 CPU。防火牆的「隱身模式」（系統設定 › 網路 › 防火牆裡）也要關掉：oMLX #3585 的回報者就是因為它，對端不回應探測，oMLX 判定「No verified shared path」而退回 TCP ring。公司配發、由 MDM 管理的 Mac 可能預設開著。

    macOS 27 把 RDMA 開關搬到系統設定了：「隱私權與安全性 › 開發者工具」裡搜尋 RDMA，打開「RDMA over Thunderbolt」，Mac 會重開機完成啟用。Macotakara 用 M5 Ultra 256GB 實測過，Apple 自己的 Harbor 截圖也是把使用者導到「Privacy & Security」實測。Apple 的 TN3205（11/19 查，最後修訂仍是 4/13）沒有跟著改，仍只寫 Recovery＋rdma_ctl enable；第三方的 d-inference 兩台文件也寫 macOS 27 在「隱私權與安全性」打開。Macotakara 同一篇也提醒：M5 Ultra 256GB 配 M4 Max 128GB 時，MLX 把模型平均切，每台只用得到 128GB，兩台效能不同時大模型還會 timeout，所以兩台最好同規格。

    設定步驟

    1. 同步系統。兩台設不同的主機名稱（例如 studio-a、studio-b），macOS 升到完全相同的版本（27 以上，連 beta 號都要一樣）。升級前先確認 runtime 支援新版：TensorFold 的兩台模式在 macOS 27.0 能跑、27.2 上 release 版就起不來（#3158）。macOS 不能透過 SSH 升級，要用螢幕共享。
    2. 每台各開一次 RDMA。macOS 27：系統設定 › 隱私權與安全性 › 開發者工具，搜尋 RDMA，打開「RDMA over Thunderbolt」，Mac 會自己重開機。會重開機，第一次要在機器前或用螢幕共享做。還停在 26.2 的話，要進 Recovery：關機 → 長按電源鍵到出現啟動選項 → 選項 → 工具程式 › 終端機 → rdma_ctl enable → 重開機。開完用 rdma_ctl status 確認。
    3. 不要讓它睡著。關閉 idle sleep（Thunderbolt 不支援 Wake-on-LAN）、開啟自動登入和停電後自動開機，例如 sudo pmset -a sleep 0 disksleep 0 autorestart 1。
    4. 互相免密碼 SSH。打開「遠端登入」，用 ssh-keygen -t ed25519、ssh-copy-id，並在 ~/.ssh/config 設好別名，也不要再詢問 host key。
    5. 先接一條線確認 RDMA。ibv_devices 要看到 rdma_en*；ibv_devinfo 要顯示 PORT_ACTIVE、transport: Thunderbolt。
    6. 停用 Thunderbolt Bridge，每條線一個子網。用 mlx.distributed_config --auto-setup 自動完成；手動設的話，兩條線例如 192.168.201.1／.2 和 192.168.202.1／.2，不設 router。
    7. 每次開機都調 wired limit。256GB 的機器例如 sudo sysctl iogpu.wired_limit_mb=235520（230 GiB），寫成 LaunchDaemon 推估。
    8. 模型放在兩台相同的絕對路徑。oMLX 和 ds4 都要求每台有一份完整的模型。
    9. 接第二條線。重跑第 5、6 步，hostfile 改成列兩個裝置。

    MLX 這一層

    版本以 MLX 0.32.4、mlx-lm 0.32.2 為準。指令格式取自 MLX 文件，路徑和主機名稱是範例。

    # 兩台都做，路徑必須一樣（mlx.launch 會 SSH 到對方執行同一個 python）
uv venv --seed --python 3.12 ~/llm/.venv
uv pip install --python ~/llm/.venv/bin/python -U mlx mlx-lm

# 在 A 上：畫出線路圖，確認兩條線都在（要先 brew install graphviz）
~/llm/.venv/bin/mlx.distributed_config --verbose --hosts studio-a,studio-b \
  --over thunderbolt --dot | dot -Tpng | open -f -a Preview

# 在 A 上：停用 bridge、替每條線設子網、輸出 hostfile（兩台都要能免密碼 sudo）
~/llm/.venv/bin/mlx.distributed_config --verbose --hosts studio-a,studio-b \
  --over thunderbolt --backend jaccl --auto-setup --output ~/llm/hostfile.json

    兩條線時 hostfile 長這樣。ips 只有 rank 0 要填 A 機在管理網路上的 IP；rdma 依 rank 順序列出連到每個 peer 的裝置，自己的位置填 null，兩邊 list 的第 k 個裝置必須接在同一條線上。裝置名稱以 ibv_devices 的實際輸出為準。

    [
  {"ssh": "studio-a", "ips": ["<A 的 10GbE IP>"], "rdma": [null, ["rdma_en2", "rdma_en3"]]},
  {"ssh": "studio-b", "ips": [], "rdma": [["rdma_en2", "rdma_en3"], null]}
]

    接好後先拿 Apple 文章裡的 Mistral Medium 3.5 128B（FP8，單台 256GB 也放得下）校準：依序跑單機、兩台 pipeline、兩台 tensor，對照 Apple 的 decode 7.70／7.70／13.69 tok/s。兩台 tensor 遠低於 13 tok/s，就是沒有走到 RDMA。先不要加 MLX_METAL_FAST_SYNCH=1。

    # 先跑 pipeline，再拿掉 --pipeline 跑 tensor parallel
~/llm/.venv/bin/mlx.launch --verbose --backend jaccl --hostfile ~/llm/hostfile.json -- \
  ~/llm/.venv/bin/mlx_lm.benchmark --model mistralai/Mistral-Medium-3.5-128B \
  -p 8192 -g 128 -b 1 --prefill-step-size 8192 --pipeline

    DeepSeek、GLM：oMLX 叢集

    兩台裝同一版 oMLX，MLX 和 mlx-lm 的版本也要一致。用 0.8.0 以上：多格 cache、CED、DeepSeek tool call 的修正（#5178）都在裡面。tensor parallel 不開 MLX_METAL_FAST_SYNCH 時 decode 約只有一半 推估，開了有卡死的風險；第一次載入如果出現 GPU timeout（#5221），多半是一台比另一台晚了 5 秒以上。RDMA 要在 oMLX 之外先設好，用 rdma_ctl status 和 ibv_devices 確認。在「設定 › 進階」打開 Distributed Inference，GUI 可以選兩台 Mac，DeepSeek 會被規劃成 tensor parallel。啟動後檢查四件事：用的是 JACCL 而不是 ring（UI 會顯示退回原因）；Model Settings 裡的 MTP、CED 有沒有被丟掉（#3071）；log 裡的 prompt cache 格數；SSD 快照上限是否從預設的 20 GiB 調大。Claude Code 把 base URL 指到 A 機的 oMLX。

    DeepSeek 備案：ds4

    ds4 沒有正式 release，要從 main 編譯，兩台必須跑同一個 commit。網路協定沒有認證也沒有加密，只能跑在 Thunderbolt 直連線上。兩台都要放完整的 V4.1 MXFP4 GGUF（467 GiB，下載合併時暫時要約 935 GiB），2TB 會很緊。下面只列文件寫明的旗標，其他參數照官方文件填。

    # B（worker）
./ds4 --tensor-parallel --role worker --coordinator <A 的 TB 埠 IP> 9911 --transport rdma \
  --dspark --mtp-model <V4.1 support GGUF> …
# A（coordinator；ds4-server 提供 Anthropic 相容端點）
./ds4-server --tensor-parallel --role coordinator --listen … --transport rdma \
  --dspark --mtp-model <V4.1 support GGUF> …
# Claude Code
ANTHROPIC_BASE_URL=http://127.0.0.1:8000 claude

    MiniMax 只能走 mlx-lm main：兩台都裝 git+https://github.com/ml-explore/mlx-lm，在 A 上用 mlx.launch --backend jaccl --hostfile ~/llm/hostfile.json -- ~/llm/.venv/bin/python -m mlx_lm server --model <路徑> 啟動，加 --pipeline 改成 pipeline。這個指令是依 Apple 文章的說明組出來的 推估，只有 OpenAI 相容 API。exo 安裝最簡單（brew install --cask exo，會自動停用 bridge、互相發現，API 在 localhost:52415，也有 /v1/messages）。main 11/1 起四個模型都能跑（DeepSeek、MiniMax 官方精度，GLM、Qwen 只有 4-bit），但還沒進 release，cask 裝到的 v1.0.71 跑不了（main 11/6 之後沒有新 commit）；不要跟 MLX 路線同時跑。DeepSeek 想要 DSpark 又要 Anthropic API，可以改用 mlx-serve 的 --dist tensor（v26.11.2 起）。llama.cpp 是在 B 機跑 rpc-server、A 機的 llama-server --rpc 指過去，按層切，只換到容量。

    下單前要確認

    • 晶片。報價單要看到「36 核心 CPU、80 核心 GPU」。30 核／64 核的頻寬一樣，但 GPU 少 20%，prefill 會再輸一截。
    • 限購和配置。台灣官網每位顧客限購兩部 Mac Studio，兩台的晶片、記憶體、SSD 要相同。
    • SSD。叢集模式每台都要放完整的模型：DeepSeek 512 GB、GLM 8-bit 343 GB、MiniMax 252 GB 兩台都要放，A 機再加 Qwen 195 GB，合計約 1.3 TB，跟單台一樣吃緊。還要放 ds4 的 GGUF 的話，2TB 放不下 推估。
    • 交期。11/19 官網（36 核／80 核）：256GB 出貨 11–12 週、512GB 9–10 週、96GB 4–5 週。現在下單，一台 512GB 約 2027 年 1 月下旬出貨，兩台 256GB 約 2 月上旬，反而晚兩週 推估。下單前在選配頁再看一次。

    穩定性

    叢集沒有 failover，可用度是兩台可用度的乘積。日常維運也多一倍：兩台都要開 RDMA（macOS 27 改在系統設定，不用再進 Recovery），macOS 要同步升級而且不能透過 SSH 做，wired limit 每次開機都要重設，出事時兩台都要重開。

    • 對端消失會卡死，GitHub 上關了，實際沒驗證。MLX #3910（7/24）：對端消失時 recv 會無限自旋，沒有錯誤也沒有 log；改用 SIGKILL 之後，wired 記憶體會被鎖到重開機。11/3 維護者把它併進 #4278，#4278 再以「Closed by #4767」關閉。但 #4767 只測了拔線，沒測對端行程被殺、線還連著的情況，#3910 底下的分析說這種情況 verbs 層什麼都不回報。11/18 mlx-serve #1237 又有一筆：兩台 M3 Ultra 的 tensor parallel 在短的重複 prompt 上卡死，殺掉 process 後兩台 GPU 仍是 100%、約 314–332 GB 被鎖住，要兩台都重開（回報者換過 libjaccl，不能排除是它）社群回報。mlx-serve 的文件也寫對端在協定中途消失會讓另一台在 Apple 的 RDMA library 裡 crash。
    • 拔線兩台一起當，MLX 0.32.5 已修。MLX #4192（8/11）：拔掉一端的線，兩台會一起 segfault。10/30 由 #4767 關閉：拔線後兩端在約 300 ms 內丟出可以捕捉的錯誤（作者實測 9/9 次）。11/25 的 MLX v0.32.5 終於含 #4767，oMLX main 同一天跟上（#5652），但 oMLX 最新正式版 0.8.3 仍釘在 mlx==0.32.4，要等下一版；上層的 runtime 也要自己拆掉 group 重建。
    • DeepSeek 長 context 的 cache 失效和逾時。oMLX #5643（11/25）：兩台 M5 Ultra 256GB 用 0.8.3 跑 DeepSeek，叢集終於跑起來，但 context 用到約 300K 之後每輪都重算 cache，首 token 要等幾分鐘；400–420K 常出現 rank-zero inference stream timed out: no rank-zero data for 300s，一輪從幾秒變成 9 分 14 秒。沒寫是 tensor parallel 還是 pipeline、用哪個量化。同一人的 #5619：叢集不收 DeepSeek 官方 FP8，要先轉成 oQ 社群回報。另一筆 #5550（11/23）：0.8.3 在 M5 Ultra 256GB 上載 DeepSeek oQ2.5h 到 172 GiB 時被 macOS 以 low-swap 殺掉，0.8.2 正常。
    • Engram 放 SSD 時的 watchdog panic 有避開的方法。oMLX #4981：256GB 跑 DeepSeek 一定要把 Engram 放 SSD，GPU keep-warm 的 300 秒一過，閒置模型的 wired 記憶體會從約 211 GB 掉到 4.4 GB，下一次大 prefill 重新 wire 時 watchdog panic。11/23–11/25 三位使用者在 0.8.3 上確認（含兩台 M5 Ultra 256GB），在 omlx serve 的環境設 MLX_METAL_RESIDENCY_REFRESH_INTERVAL_MS=1000 後沒再當 社群回報。兩台都要設。
    • Tensor parallel 的 GPU timeout。oMLX #5221（11/12）：0.8.0rc1 的 DeepSeek tensor parallel 第一個 prefill 就 GPU timeout，兩個 rank 一起退出；另一位在兩台 M5 Ultra 256GB 上裝完 rc1 的頭兩次載入也遇到。維護者：兩台每一層都在 GPU 上互等，一台晚超過約 5 秒，Metal 就取消另一台的工作。256GB 的 DeepSeek 必須從 SSD 讀 Engram，正是會讓一台突然變慢的情況 推估。
    • macOS 27.2 和 TensorFold。TensorFold 的兩台模式讓 GPU 在 command buffer 裡等對方寫入的旗標，macOS 27.2 上看不到，release 版的 GLM、Qwen 兩台模式都起不來（#3158、#3408）；社群修正還在 draft。11/22 第二對 M5 Ultra 512GB（macOS 27.2.1）用修正版 #3688 跑 Flash Next：兩台的 decode 比單台慢 7–10%（drafted 133.6 對 143.7），8K、16K prompt 約快 1.75 倍，1K prompt 兩台反而慢，輸出逐 token 相同 社群回報。換 macOS 小版本也可能讓叢集壞掉。
    • 重疊請求凍住。oMLX #3039：兩台 M4 Max 走 JACCL 的 tensor parallel，兩個重疊的串流請求讓兩個 rank 在 collective 裡凍住、各吃 100% CPU，heartbeat 還顯示正常，SIGTERM 無效。11/5 被 stale bot 關掉，沒有修。mlx-serve 的兩台 tensor parallel 也記錄過一次 Fence::wait 卡住，之後 25 輪沒再重現 社群回報。
    • 線路自己掉。有人在 5 台 M3 Ultra 上遇過兩次線路掉線造成的 production crash，當掉的機器約有 140GB 記憶體被鎖住 社群回報。
    • 長 prompt 的 GPU timeout。長 prefill 會觸發 Metal GPU timeout，接著連鎖出現「Couldn't allocate protection domain」，要把 prefill-step-size 降到 2048 並清掉殘留的 process 社群回報。
    • Kernel panic。2026 年 1 月有人在 5 台 M3 Ultra 上整理出 21 次 kernel panic，懷疑跟 RDMA driver 有關。MLX 維護者對 GPU timeout 的回應是還沒有好的通用解法 社群回報。
    • oMLX 叢集自己的 issue。per-model 設定會被悄悄丟掉（#3071）；pipeline 在 sampling_rank_only 時會 deadlock（#3521，11/19 被 bot 以過期關閉，沒有修正）；早期版本的 SSD prompt cache 在叢集拆掉後留下 226 GB＋239 GB 的檔案（#3422，現在有 20 GiB 的預設上限）。10/30 回報的同一個 deployment 第二次啟動就失敗（#4973）已在 0.7.3 修好；canary 失敗後 rank 殘留、只能重開 app（#4968）還開著；#3585 的「悄悄退回 TCP」原因是防火牆的隱身模式，已寫進怎麼串聯。11/17 又有人從原始碼發現：連線檢查只 ping 一次（隱身模式會丟 ICMP），mDNS 掉一個封包就判對端死掉（#5381、#5382，修正 PR 還開著）；三台 mesh 部署一律失敗（#5394）。
    • 還是要買的話。準備一支一鍵重啟的 script（kill、兩台重開、設 wired limit、重新 launch），把線材固定好避免拉扯，並接 UPS。

    什麼時候重新評估

    出現下面任何一項，就值得重新評估兩台（或 512GB 再加一台）的方案。11/26 的狀況是：MLX 0.32.5 終於含斷線修正，但 oMLX 正式版還沒帶；兩台跑 DeepSeek 第一次有長時間使用的回報，結果是 300K 以上 cache 失效、400K 附近逾時（#5643）；第二筆同 runtime 的兩台對單台（TensorFold 跑 Flash Next）decode 仍比單台慢 7–10%。主力候選只剩 DeepSeek 和 MiniMax，都放得進 512GB，所以建議仍是一台 512GB。

    • Prompt cache。oMLX 叢集拿掉 1 格 RAM cache 的限制（#3062），或公開 Claude Code 在 SSD 快照上的命中率。11/19 現況：成立一半。#5062 已進 0.8.0 正式版（11/18），叢集 RAM cache 依餘裕給 2／4／8 格（balanced 8）。仍然只在單機模擬驗證，沒有兩台實機、沒有 Claude Code 的命中率；byte 上限仍關閉。mlx-serve 的兩台 tensor parallel 也有 RAM＋SSD prefix cache。
    • 實測。有人公開兩台 M5 Ultra 走 JACCL（不是 ring）跑 DeepSeek 或 GLM 的數字，decode 比單機快至少 1.3 倍，而且確認 CED 在叢集裡有效。11/19 現況：沒有成立，新證據偏負面。DeepSeek 只有 mlx-serve 的 63.3／62.7 tok/s（沒有單機 512GB 基準）和不對稱的 45–52 tok/s（#5272，11/21 進了 0.8.1 正式版，仍不是兩台 M5 Ultra）；同 runtime 的兩台對單台（TensorFold 跑 Qwen）decode 是 0.87–0.91 倍，不是 1.3 倍。GLM 有 d-inference 的 4-bit 等級 pipeline 數字，沒有單機基準；8-bit 只有 oQ8e 跑起來（只驗 tool call）。CED 已進 0.8.0，開關有送到 tensor parallel rank，但沒有兩台 M5 Ultra 的數字。
    • 穩定性。MLX 合併死節點偵測，修好 #3910 和 #4192。11/26 現況：一半。MLX v0.32.5（11/25）含 #4767，oMLX main 已跟上，正式版 0.8.3 還沒；#5643 是兩台跑 DeepSeek 第一份長時間使用的回報，300K 以上 cache 失效、400K 附近逾時。11/19 現況：沒有成立，比 11/11 更差。MLX 仍沒有含 #4767 的 release，oMLX 0.8.0 仍釘在 mlx==0.32.4（11/21 的 0.8.1 也一樣）；沒有人驗證行程被殺的情況，反而多了三筆負面回報：oMLX #5221（tensor parallel 啟動時 GPU timeout，兩台 M5 Ultra 256GB 也遇過）、mlx-serve #1237（卡死，殺掉後要兩台重開）、TensorFold #3158／#3408（macOS 27.2 上兩台模式起不來）。oMLX #3039（重疊請求凍住）仍沒修。
    • MiniMax。叢集 runtime 拿回 DSpark 和 Anthropic API。11/19 現況：成立一半，沒有變。exo main 能切官方 NVFP4、有 /v1/messages，但 11/6 之後沒有新 commit、沒有 release、沒有 DSpark；oMLX 叢集的 MiniMax 仍沒有成功回報（#4827）。

    能跑哪些小模型

    這台卡在算力，不是記憶體。Qwen3.8-27B 的 4-bit 放得下（約 19 GiB），但它是 dense 模型，同款機器實測 prefill 只有 52–55 tok/s、decode 約 10 tok/s。Claude Code 第一輪約 30K token，要等 9–10 分鐘才出第一個字；朋友的 5090 prefill 約 2,300 tok/s，同樣的 prompt 十幾秒就讀完。所以 27B 在這台只適合 8K 以內、可以等的單次問答。用跟 Mac 分頁同一條 DeepSWE 門檻篩過、又跑得動 Claude Code 的只有 Inkling 2 Mini：DeepSWE 48.2，比 27B 的 42.2 高，30K 首字約 2.5–3 分鐘。但 oMLX 0.8.3 在 M1 上跑它每個請求都會失敗，修正 11/25 才進 main，要等下一版。現在就能用、速度最好的是 Qwen3.6-35B-A3B（3B active 的 MoE，30K 首字約 70 秒），但長時程的 agent 分數差很多，只拿來做短任務和文件問答。

    這頁的速度都來自 omlx.ai 上同款機器（M1 Pro 16 核 GPU、32GB）的社群上傳，或從 M1 Max、M2 Max 的數字換算，沒有一筆是這台自己量的。分數都是各家自報，只有少數幾張表用同一套 harness 量了好幾個模型，見門檻與候選。研究筆記在 research_notes/2026-11-26 全面更新/m1pro_32gb.md。

    硬體與記憶體

    這台機器

    • 晶片：M1 Pro，GPU 14 核或 16 核（14 吋的基本款是 14 核，16 核是選配，看「關於這台 Mac」）。FP32 算力約 4.6／5.3 TFLOPS 推估。
    • 記憶體：32GB，頻寬 200 GB/s，是 M5 Ultra 的六分之一。
    • 沒有 Neural Accelerator。oMLX 的 M5 專用 kernel、A8 prefill 都用不到；oMLX 的 ANE prefill 會另外 wire 記憶體（27B 8-bit 要多保留 7 GiB），在 32GB 上不可行。
    • M1 沒有原生 bf16。MLX 遇到 bf16 的 checkpoint 會用模擬的方式算，prefill 慢很多。oMLX 的 Float16 Activations（只對 M1、M2 開放）載入時把 bf16 參數轉成 fp16：同一台 M1 Pro 跑 Qwen3.6-27B，prefill 從 42 變成 70–74 tok/s 社群回報。少數模型在 fp16 會溢位出 NaN（Flint #4784 還開著；Inkling 的已在 0.8.3 修好）。
    • M1 的 threadgroup 上限是 448，新模型常撞到：Qwen3.8 的 MTP verify（#4913，已修）、Inkling 2 Mini（#5570，0.8.3 每個請求都失敗，11/25 修正進 main）。

    記憶體怎麼分

    GPU 能用多少記憶體（Metal 的 recommendedMaxWorkingSetSize）跟 macOS 版本有關 社群回報：

    • macOS 13–15：21,845 MiB（剛好 2/3）。
    • macOS 26／27：約 25,559 MiB（約 78%）。

    要調高用 sudo sysctl iogpu.wired_limit_mb=<MiB>，重開機就還原，永久生效要寫成 LaunchDaemon。公司 MDM 管的筆電可能沒有管理員權限，要先問 IT。

    這台還要開 IDE、瀏覽器和通訊軟體，抓 10–12 GB 給 macOS 和這些 app，所以模型、KV 和暫存合計要壓在 20–22 GB 推估。有人在 M4 32GB 上只留 6 GB 就失敗，建議留 9 GB；另一份回報是 Docker 佔掉 24 GB 時載入 18 GB 的模型，M1 Pro 32GB 直接 kernel panic，因為 llama.cpp 只看 Metal 的上限、不看實際剩多少 社群回報。跑的時候開著「活動監視器」看記憶體壓力，不要讓它進 swap。

    Qwen3.8-27B 適不適合

    模型本身

    8/5 釋出，Apache-2.0，27B dense，架構跟 Qwen3.6-27B 一樣：64 層，每 4 層裡 3 層 Gated DeltaNet、1 層 full attention，所以只有 16 層要存 KV（4 個 KV head × 256 維），每 token 64 KiB 已確認。原生 262K context、可以看圖和影片、有 MTP head，thinking 預設開（reasoning_effort 只收 xhigh、medium、low）。分數在這個尺寸很好：DeepSWE 42.2、SWE-bench Pro 61.7（都是 Claude Code harness）、Terminal-Bench 2.1 73.0。朋友覺得它聰明是對的。

    放得下。Q4_K_M 16.81 GB（15.66 GiB）加 32K 的 q8_0 KV 1.06 GiB、GDN state 0.15 GiB、compute buffer 約 1 GiB，約 18 GiB。llama.cpp 預設存 32 個 context checkpoint，每個約 150 MiB，要降到 8 個，總共約 19 GiB 推估。Q5 級（約 20 GB）是上限，Q6_K 以上加 KV 就超過預算。

    慢在 prefill，換量化救不了

    dense 模型每個 token 都要算全部 27B 參數。prefill 是算力瓶頸，M1 Pro 的 GPU 只有 5090 的幾十分之一：同款機器跑 MLX 4-bit 的 prefill 52–55 tok/s，朋友那種 5090 是 2,268–2,430，差 40 倍以上；decode 10.5 對 47–72（LM Studio 偏慢）社群回報。

    • 換小量化（UD-IQ3_XXS 10.93 GB）只會讓 decode 快一點，prefill 不會變快，IQ 系在 Metal 上還可能更慢。
    • MLX 4-bit 開 Float16 Activations 約 70 tok/s，30K 首字還是要 7–8 分鐘 推估。
    • MTP 在 M1 上沒幫助：verify 卡在 ALU，同款機器的 oQ3.5e-mtp decode 只有 6.9，比 4-bit 不開 MTP 的 10.5 還慢 社群回報。
    • 一個要 20–40 輪工具呼叫的 agent 任務，加上每輪 1,000 token 左右的 thinking（10 tok/s 就是 1.7 分鐘），會跑上一小時以上 推估。

    適合的用法：prompt 在 4–8K 以內、可以等的單次問答。4K prompt 約 1 分鐘出第一個字，再加 1–3 分鐘的輸出。它的 RL 微調版（DaisyRose-27B、sabi-noema，自報 DeepSWE 46–48）也是一樣的速度。

    接 Claude Code

    Claude Code 第一次呼叫就有 21K–40K token（看開了哪些工具），之後每輪只算新增的部分，前提是 prefix cache 有命中。這台的 prefill 慢，cache 能不能穩定命中比什麼都重要，所以先用 oMLX（RAM＋SSD 的 prompt cache、Anthropic Messages API、內建 Claude Code 的啟動設定），llama.cpp 當備案。

    • context 要設對。Claude Code 2.1.323 起把不認得的模型 ID 當成 1M context，要設 CLAUDE_CODE_MAX_CONTEXT_TOKENS 等於 server 的 context（例如 65536），否則塞滿之後每輪都失敗。到 2.1.332（11/25）都沒改。2.1.332 起，Desktop app 的 Code 分頁會忽略不是 claude 開頭的模型 ID 和低於 200K 的 CLAUDE_CODE_AUTO_COMPACT_WINDOW，接本機 server 用 CLI。
    • Qwen 的模板要換。官方 chat_template.jinja 遇到 Claude Code 中途插入的 system 訊息會丟例外（System message must be at the beginning.），server 回 400／500；上游以 not planned 關閉，要用社群修過的模板（llama.cpp 用 --chat-template-file）。Qwen3.6、Qwen3.8、Ornith 都一樣。
    • llama.cpp 上 hybrid 模型的 prefix cache 還很脆。#24055 還開著、修正 #25592 沒合併；thinking 和 tool call 周圍的空白還原不回來會整段重算（#30357）。M1 Max 上有人每輪都從第 9K token 起重算 13K token，等 174 秒。checkpoint 不能關（--ctx-checkpoints 0 會每輪重算），在這台降到 8 個。
    • Inkling 2 Mini 的行為。官方自己寫它會卡在很長的推理迴圈、做 agent 時會不確認就刪檔或覆寫、回報的結果也不一定準。Claude Code 要維持一般的權限確認、限制 output token，不要讓它自己跑長任務。llama.cpp 上它在 tool_choice=auto 時 20 次有 8 次呼叫沒宣告的 bash（#32966）。
    • thinking 會吃掉 decode 時間。Qwen3.x 預設 thinking 開、effort xhigh。這台 decode 只有 10–55 tok/s，短任務可以關 thinking（enable_thinking: false）或用 medium。Claude Code 送 max、minimal 的 effort 時，Qwen 的模板會回 400。
    • oMLX 0.8.3 起，Claude Code 的 WebSearch 工具可以在本機模型上用（#5342），由 oMLX 設定的搜尋服務回答。公司筆電上要確認這個搜尋服務能不能用。

    設定步驟

    1. 確認機器和權限。「關於這台 Mac」看 GPU 核數和 macOS 版本；問 IT 能不能裝 oMLX（DMG 要 macOS 15 以上）、能不能從 Hugging Face 下載約 20 GB 的權重、能不能用 sudo。
    2. macOS 15 以前要調 GPU 上限。預設 21,845 MiB 放不下主選的 21 GiB，用 sudo sysctl iogpu.wired_limit_mb=24576 調到 24 GiB，重開機後要重設。macOS 26、27 的預設約 25,559 MiB，不用調。
    3. 裝 oMLX 最新正式版，先跑 Qwen3.6-35B-A3B oQ3.5e-mtp。Model Settings 打開 Float16 Activations、MTP 先關，context 64K，memory guard 用 balanced。用 oMLX 內建的 benchmark 量 4K、32K 的 prefill 和 decode，把數字填回這頁。
    4. 開著 IDE 和瀏覽器再看一次記憶體。活動監視器的記憶體壓力維持綠色、沒有 swap 才算過。
    5. 接 Claude Code。從 oMLX 的 Claude Code 啟動設定開，或自己設 ANTHROPIC_BASE_URL、ANTHROPIC_MODEL、CLAUDE_CODE_MAX_CONTEXT_TOKENS=65536。換掉 Qwen 的模板。用一組固定的小任務看 tool call 成功率和 cache 命中率，再換 Ornith 跑同一組。
    6. oMLX 出 0.8.3 之後的版本時，換 Inkling 2 Mini 跑同一組任務。context 32K，關掉不用的 app。比較成功率、每輪花的時間（它很冗長）和有沒有 swap，再決定主力是 Inkling 還是 Qwen3.6。
    7. Qwen3.8-27B 只放著當問答用。MLX 4-bit、Float16 Activations、reasoning_effort: medium，prompt 8K 以內。

    其他用途

    Embedding 和 reranker

    個人規模的 RAG 可以在這台跑：Qwen3-Embedding-0.6B（Q8_0 0.64 GB）或 4B（Q4_K_M 2.50 GB）、Qwen3-Reranker-0.6B（Q8_0 0.64 GB）。從 7B 的 prefill 換算，0.6B 約 2,500–3,500 tok/s，4B 約 400–500 tok/s，100 萬 token 要 35–40 分鐘 推估。跟主力模型同時跑會搶 GPU：rerank 40 段 512 token 就等於一次 20K 的 prefill。大批文件的索引留給 M5 Ultra 或 3060 Ti 小機殼。

    M5 Ultra 到貨後當 client

    這台只跑 Claude Code，設 ANTHROPIC_BASE_URL=http://<Mac Studio>:<port>、ANTHROPIC_AUTH_TOKEN、ANTHROPIC_MODEL、CLAUDE_CODE_MAX_CONTEXT_TOKENS，本機不吃記憶體，也不用降量化。Anthropic 的文件寫明不支援透過 gateway 讓 Claude Code 接非 Claude 的模型，出問題要自己處理。公司的程式碼會送到私人的主機，要先確認公司政策。

    • 速度全部來自同款機器的社群上傳或換算，沒有一筆是這台在開著 IDE 和瀏覽器時量的。Qwen3.6-35B-A3B 在 M1 Pro 上 32K、64K 的新版 oMLX 數字沒有（4 月的 0.3.5 在 14 核上 32K 是 236）。
    • Inkling 2 Mini 的 M1 修正（#5570）11/25 進了 oMLX main，還不知道哪一版會出；32GB 機器開著 IDE 時會不會 swap 也沒有資料。它在 oMLX 上跑長時間的多輪 agent 時記憶體會一直漲（#5539，0.8.2 上 25 分鐘從 17.8 漲到 108.9 GB，還開著）。
    • 3-bit 級（oQ3.5e、IQ3_M）對 agent 分數的影響沒有資料。
    • 這個尺寸的 agent 分數幾乎都是自報，DeepSWE 只有 Inkling 2 Mini、Qwen3.8-27B、Ornith（22）和 Qwen3.6（0，Ornith 卡上的）有。Ornith 在 M1 上的速度和接 Claude Code 的 tool call 穩定度都沒有資料，Ollama 接 Claude Code 時它的 tool call 解析壞掉（#16992，還開著）。
    • Ollama 的 MLX runner 在 M1 Pro 32GB 上跑 Qwen3.6 會 panic（#18856），GGUF 版正常。
    • 長時間 prefill 會讓 GPU 滿載、風扇全速；用電池時 macOS 可能進低耗電模式，速度明顯變低。

    現有規格能做什麼

    這台撐不起 Claude Code 的主力後端，Mac 分頁追蹤的大模型也都跑不實用。它能做兩件事。M5 Ultra 到貨前，用 llama.cpp 跑 Qwen3.6-35B-A3B 的 3-bit 版，當輕量的 coding agent 和 32K–64K 的文件問答：experts 大部分放在 RAM，推估 decode 20–26 tok/s、prefill 350–1,000 tok/s。到貨後改當 RAG 的批次前處理機，跑 OCR、文件解析和大量 embedding，把吃 GPU 的批次工作從 Mac 移走。限制同時卡在 16GB RAM 和 8GB 顯存，而且 3600X 沒有內顯，螢幕和 Windows 桌面還要從顯卡吃掉約 1GB。

    到貨前
    Qwen3.6-35B-A3B UD-IQ3_XXS（13.2GB），llama.cpp 的 Windows CUDA 版，--n-cpu-moe 約 30、context 32K–64K。要速度就改 Qwen3.5-9B Q4_K_M，整個放進顯卡，但 agent 能力差一大截
    到貨後
    批次 OCR 和文件解析（PaddleOCR-VL-1.6、GLM-OCR、MinerU、Docling）、批次 embedding（Qwen3-Embedding-4B 或 8B）、rerank（Qwen3-Reranker-0.6B）。查詢時的單句 embedding 留在 Mac 上
    不建議
    Strata 跑 Qwen3.8-Flash-Next（推估 3–10 tok/s）、Strata 跑 Qwen3.6（同規格只到 16K、要量化 KV，更長就 OOM）、Qwen3.6／3.8 的 27B dense（6–8GB 的筆電卡實測 0.75–2.4 tok/s）、TensorFold（Windows 的 CUDA build 11/25 起又編得過，但仍沒有打包版；27B 放不進 8GB）、Betelgeuse（只支援 Linux 和 12GB 卡，context 512，DeepSeek 的 routing 被改過）
    接 Claude Code
    Qwen3.x 的官方 chat template 遇到 Claude Code 中途插入的 system 訊息會讓 server 回 500，到 11/19 上游仍沒修，要換修過的模板。Claude Code 2.1.323 起把不認得的模型 ID 當成 1M context，要設 CLAUDE_CODE_MAX_CONTEXT_TOKENS 等於 server 的 -c，否則塞滿 64K 後每輪都失敗。hybrid 模型的 prefix cache 在 llama.cpp 上還很脆（修正 PR #25592 還沒合併）。第一輪就有 21K–40K token，冷 prefill 要等 21 秒到約 2 分鐘
    精度
    3-bit 是這台的妥協，沒有公開的 KLD。同樣 3060 Ti 8GB 配 16GB RAM 的 Ubuntu server 有人日常用 llama.cpp 跑 UD-Q4_K_XL（22.4GB）128K，但沒附速度；在 Windows 上試，要接受部分 experts 從 SSD 讀
    還要確認
    SSD 是不是 NVMe、主機板晶片組（決定顯卡槽是 PCIe 3.0 還是 4.0）、RAM 速度、SFX 電源瓦數、Windows 10 還是 11（NVIDIA 11 月起的新驅動只支援 Windows 11）、網卡速度

    硬體與記憶體

    這台機器

    • CPU：Ryzen 5 3600X，Zen 2，6 核 12 緒，有 AVX2、沒有 AVX-512，沒有內顯。
    • RAM：16GB DDR4，兩個插槽都用掉了。這頁假設是 2×8GB 雙通道；速度還不確定，DDR4-3200 雙通道理論上是 51.2 GB/s。
    • 顯卡：RTX 3060 Ti 8GB GDDR6，Ampere（sm_86），頻寬 448 GB/s。CUDA 實際看到 7,838 MiB。
    • 系統：Windows，10 或 11 還不確定。NVIDIA 2026 年 11 月起的新驅動只支援 Windows 11，Windows 10 停在 10 月的驅動，之後只有每季的安全更新。那一版仍是 R580 以上，llama.cpp 的 CUDA 12.4 和 13.5 兩包都還能用。SSD、主機板晶片組和網卡速度還不確定。

    3600X 在 X570、B550 上，顯卡槽是 PCIe 4.0；在 B450、X470、A520 上是 3.0。小機殼常用的 riser 也可能被迫跑 Gen3。PCIe 只影響 prefill，decode 時 CPU 端的 experts 就在 CPU 上算，幾乎不走 PCIe。

    記憶體怎麼分

    以 Qwen3.6-35B-A3B UD-IQ3_XXS 為例 推估。

    顯存。7,838 MiB 扣掉桌面和瀏覽器約 1GB，剩約 6.8GB。卡上要放非 expert 權重（約 2.8B 參數，1.6–1.9GB）、64K 的 q8_0 KV（約 0.7GB）和 -ub 2048 的 compute buffer（約 1.0–1.5GB，沒人量過）。剩下約 3GB，每層 experts 約 0.29GB，放得下 9–11 層，所以 --n-cpu-moe 大約 29–31。

    RAM。CPU 端的 experts 約 8.7GB，加上 Windows 11 開機約 3.5–5GB 和 llama-server 本身，合計 13.5–15GB。跑的時候要關掉瀏覽器，Claude Code 的 client 放在 Mac 上跑。Q4 等級（Q3_K_S 15.4GB 以上）就放不下了，UD-Q2_K_XL（12.3GB）是保留餘裕的備案。

    如果之後換成 2×32GB。這頁以現有的 16GB 為準。順帶一提，兩個插槽換成 2×32GB 就是另一個等級：同樣是 8GB 卡，RTX 3070 Laptop 配 63.4 GiB RAM 在 Windows 上用 Strata 跑 Qwen3.8-Flash-Next IQ3_XXS，decode 36.1、prompt 503–549 tok/s 社群回報。要先確認主機板支援單條 32GB。

    Decode 怎麼推

    從 3070 桌機配 3700X 跑 IQ4_XS 的 27.0 出發。3600X 少兩個核心，CPU 端 experts 的計算大約打八折；IQ3_XXS 每個 token 讀的資料比 IQ4_XS 少約兩成，但 IQ 系的 dequant 在 CPU 上是算力瓶頸，兩者大致抵銷。長 context 的降幅用 3060 Laptop 的深度測試：16K 掉 15%、49K 掉 32%。DDR4 的頻寬其實用不滿：3060 Laptop 每個 token 從 RAM 讀約 560MB、跑 34 tok/s，只用到約 19 GB/s，瓶頸是 CPU 計算和同步，所以 6 核比 RAM 頻寬更限制速度。信心中低。

    Prefill 怎麼推

    3070 的 pp512 是 517，3060 Laptop 在 server 上是 256–317，這是預設 ubatch 的範圍。prefill 時 llama.cpp 會把 CPU 端的 experts 逐個 ubatch 搬到顯卡上算，ubatch 越大，搬一次能算越多 token，是最大的槓桿：3060 12GB 實測快 2.5–3 倍，PCIe 3.0 時的 bus 用量也從 6.1–7.2 GB/s 降到 0.7–3.8 GB/s。3060 12GB 用 -ub 2048 到 1,328，但它卡上多放了約 4 層 experts。8GB 卡上 -ub 2048 的 compute buffer 實際多大沒有資料，所以信心低。

    Prefix cache 很脆

    Qwen3.6 是 hybrid 模型（30 層 Gated DeltaNet 加 10 層 full attention），llama.cpp 不能像一般 KV 那樣從中間截斷重用，只能回到 checkpoint。checkpoint 只建在 user 訊息的起點和 prompt 結尾前的幾個位置，最後一個 checkpoint 之前有任何改變就整段重算。#24055（checkpoint 一直被判失效，回報者之一就是 RTX 3060 12GB、Windows、Qwen3.6；11/12 又有人回報 system prompt 中間改一行就整段重算）和 #30357（think、tool_call 周圍的空白還原不了）都還開著。修正 PR #25592 讓 checkpoint 只在存的位置還原、prompt 結尾的 checkpoint 不受 --checkpoint-min-step 限制，11/15 有人回報可用，但還沒合併。11/15–11/17 合併的 slot 排程重構修的是 SWA 加 recurrent 的模型，Qwen3.6 不受影響。--checkpoint-min-step 預設 8,192，Claude Code 第一輪的 prompt 裡只會留很少幾個 checkpoint；單 slot 可以試 2,048，用 --ctx-checkpoints 12 封頂。每個 checkpoint 約 63 MiB，預設 32 個就是約 2GB RAM，這台建議 --ctx-checkpoints 8–16、--cache-ram 約 2,048。

    Claude Code 要告訴它 context 只有 64K。Claude Code 2.1.323（11/12）起，把不認得的模型 ID 預設當成 1M context，塞滿 llama-server 的 64K 之後會每輪失敗，直到 /clear。2.1.325（11/13）起，CLAUDE_CODE_MAX_CONTEXT_TOKENS 對不認得的模型 ID 都生效。在 Mac 上設 ANTHROPIC_MODEL=qwen3.6-35b-a3b、CLAUDE_CODE_MAX_CONTEXT_TOKENS=65536（跟 -c 一樣，或略小）；llama-server 加 --alias qwen3.6-35b-a3b。

    輕量 agent 可以，Claude Code 主力不行。單檔修改、短任務、32K–64K 以內的文件問答做得到。長 session、大型 repo、128K 以上的工作，冷 prefill 和 cache 失效的代價太高。Qwen3.6 接 Claude Code 的工具呼叫成功率和 cache 命中率也還沒有人公開量過。

    TensorFold 的 27B 新聞

    11/11 X 上流傳的「Qwen3.8-27B 單張 RTX 5090 破 1,000 tok/s」，量的不是單一請求的 decode。satellitedown 用自己的 engine Cinference（NInfer 的 fork，不是 TensorFold）把一個 prompt 拆成 8 條 lane 同時寫，8 條加總後最快那一秒是 1,623、整段平均 decode 1,099 tok/s，他自己說實際使用約 350。TensorFold 同一天的 fanout 模式也是多條 lane 加總：作者用 4 條 lane 寫 prose 約 300 tok/s，社群用 8 條 lane 瞬間最高約 926 社群回報；fanout 到 11/19（1.2.10）還沒放進 repo，每條 lane 是否 lossless 仍無從確認。

    TensorFold 跑 27B 單一請求的數字：RTX 5090 上 prose 215–279、code 434–539 tok/s；RTX 3090 上（v1.2.7 的 Linux release，EXL3 3.00 bpw 加 DFlash2）code 184、prose 84，不開 draft 約 30.5，開不開 draft 的輸出逐 token 相同 實測。套到這台都用不上：

    • 放不下。27B 最小的 EXL3 3.00 bpw 載入就要 13.78 GiB。TensorFold 的 CUDA engine 要求權重整個放進顯存，不能像 llama.cpp 那樣把一部分放在 RAM。改用 llama.cpp 部分 offload 的 dense 27B，在 6–8GB 的筆電卡上只有 0.75–2.4 tok/s。
    • Windows 要自己編。官方文件寫「Windows is supported from source only」：要 Zig 0.17、CUDA Toolkit 13 和 MSVC，用 -Dsm=86 編。唯一的打包 Windows 版 PR（#2809，只針對 RTX 5090）在 11/14 以 stale 關閉，release 仍只有 Linux 和 macOS。Linux release 有 sm_86 的 kernel，要 R580 以上的驅動。
    • 放得進 8GB 的只有小模型。Qwen3.5-2B、LightOnOCR-3 0.8B，以及 1.2.8（11/13）起 CUDA 能跑的 Qwen3-Embedding 和 Qwen3-Reranker。後兩個只吃 BF16，8GB 卡只放得下 0.6B，而且都只在 DGX Spark（GB10）上驗證過。這台要做 embedding 或 OCR，用 llama.cpp 比較省事。

    TensorFold 這兩天對 Mac 分頁比較有用的是另外兩件事：DeepSeek 官方權重在 M5 Ultra 512GB 上的實測（#1720），以及 GLM 在單台 512GB 上的六組比較，已經寫進 Mac 分頁的 TensorFold 一節。

    Betelgeuse 的 DeepSeek 新聞

    Betelgeuse 是 llama.cpp 的 fork，單一作者，10/31 出 v0.6.0。它號稱在 RTX 3060 12GB、16GB RAM 加 NVMe 上跑 748B 的 DeepSeek V4.1 Flash 1017，decode 18.92 tok/s。做法是 dense 權重放顯卡，routed experts 放 NVMe，用顯卡上的 expert slot 和 8 GiB 的 pinned RAM cache 分層，需要時才用 io_uring 讀。另外支援 Qwen3.8-Flash-Next 的 2-bit 版（68 GB）。README 自己標 experimental，只認證 Linux、sm_86 和 12GB 卡。11/19 查了原始碼、工作紀錄和 issue，結論是這台用不上。

    • 數字的條件很窄。context 512、單 slot、temperature 0，同一個 binary_search 續寫 prompt 跑第三次才有 18.92，第一次只有 5.58。prefill 的 61.80 也是同一個 64-token prompt 重跑，第一次是 6.83。DeepSeek 的設定還關掉 prompt cache。量化是 Unsloth 的 UD-Q2_K_XL 加 IQ4_NL Engram，約 310 GB，跟原模型的 top-1 一致率 91.5%（見 Mac 分頁）社群回報。
    • DeepSeek 的 routing 被改過。README 寫「Nothing is pruned, skipped」，但作者的工作紀錄（TASK.md）寫明：每個 token 的 6 個 experts 裡，只有第一名照模型的 router 選，必要時從 SSD 讀；另外 5 個改成從每層常駐的少數 experts（最後是顯卡上 5 個、RAM 裡最多 2 個）裡挑分數最高的，不在常駐集合裡的就不讀。這是有損的近似，作者沒有公布 KL、PPL 或任何 benchmark。唯一的品質檢查是那個續寫看起來正確，而規則就是對著這個 prompt 調出來的。
    • Qwen 的 routing 是精確的，但只有 2-bit。作者比對過全部 28,080 筆原始 router 紀錄。量化是 ISTA 的 GSQ-RCO IQ2_XS，KL 沒有公布。22-token prompt 的 decode 第一次 13.87–16.80、重跑 21.43–22.03 tok/s，prefill 13.85–19.35 社群回報。11/7 合併 DeepSeek 的程式之後，main 分支跑 Qwen 會在建立 context 時失敗（#4），只能用 v0.6.0。
    • 第三方回報都是 Qwen、context 512。RTX 3090 24GB 在 WSL2 上 decode 12.6–12.7、prefill 15–18 tok/s，顯存用掉 16.9 GB；原生 Ubuntu 第一次 8.02、之後 17.11–21.19 實測。RTX 5060 Ti 在 WSL2 上開 64K context、送約 6,000 token 的 prompt，prefill 只有 2.2 tok/s，約 4 分鐘後 Windows 藍屏（DPC_WATCHDOG_VIOLATION，NVIDIA 驅動），關掉它常駐的 polling kernel 輸出就變亂碼 社群回報。作者說在做 v0.6.1（Ada、Blackwell 原生支援和 MTP），還沒有時程。
    • 放到這台。3060 Ti 也是 sm_86，但只有 8GB：DeepSeek 的設定顯存峰值 11.1 GiB，Qwen 的 5,000 個 slot 約 7.2 GB 加上 dense 3.77 GB 也放不下，要砍 slot，速度會再掉 推估。這台是 Windows，原生編不過，WSL2 有上面的藍屏回報。context 512 連 Claude Code 的第一輪（21K–40K token）都裝不下；就算放寬，15–60 tok/s 的 prefill 讀 40K 也要 11–45 分鐘。現在推薦的 llama.cpp 跑 Qwen3.6-35B-A3B 有 32K–64K context、Anthropic API 和 prompt cache，實用得多。

    到貨後當輔助機

    M5 Ultra 的 512GB 扣掉主模型，RAG 全套（20GB 以內）一定放得下，所以問題不在記憶體，在 GPU 算力的競爭。查詢時的 embedding（20–50 token）只要幾毫秒，不值得移出去。批次 embedding（動輒百萬 token）、OCR（一跑幾小時）和 rerank（40 段 512 token 就等於一次 20K token 的 prefill）會跟 coding agent 的 prefill 搶 GPU，最值得移到這台。llama.cpp 的 7B 基準 prefill，3060 Ti 約是 M5 Ultra 的 0.6 倍（2,991 對 4,945）、M1 Mac mini 的 25 倍（M1 只有 118），所以 M1 只適合放向量資料庫和 gateway。網路不是瓶頸：一個 1024 維的向量只有 4KB，掃描頁一秒傳不到一頁，Gigabit 綽綽有餘。

    設定步驟

    1. 先確認硬體。SSD 是不是 NVMe（mmap 冷載入從這裡讀）、主機板晶片組（決定 PCIe 3.0 還是 4.0）、電源瓦數、Windows 10 還是 11、網卡速度。BIOS 確認有開 XMP 或 DOCP 到 3200、FCLK 1:1。
    2. 關掉 Sysmem Fallback。NVIDIA 控制面板 › 管理 3D 設定 › 程式設定，加入 llama-server.exe，把「CUDA - Sysmem Fallback Policy」改成「Prefer No Sysmem Fallback」。預設會在顯存用完時改用系統記憶體，超出約 100MB 就靜靜慢 3–6 倍；關掉之後溢位會直接 OOM，比較容易發現。--fit 只在載入時檢查，執行中溢位一樣會掉速。
    3. 騰出顯存和 RAM。能不接螢幕就不接，用 SSH 或遠端桌面管理；關掉瀏覽器和其他程式的硬體加速。pagefile 放在 NVMe 上，系統管理或固定 16–32GB，初始大小要夠大。載入方式用 -lm（--no-mmap、--mlock 已經拿掉了）。預設 auto 就是 mmap；-lm dio 在 Windows 上 11/09 起才真的不經過 file cache。llama-bench 時兩種都量：mmap 開機後的第一個請求可能很慢（6GB 卡在 Linux 上實測，冷 mmap 只有 0.035 tok/s），dio 只把 CPU 端約 8.7GB 的 experts 讀進 RAM，但那是私有記憶體，pagefile 要夠大。
    4. 裝 llama.cpp。從 GitHub release 下載 b12532 以後的 win-cuda-12.4-x64 或 win-cuda-13.5-x64（v1.0.0 之後；b12391 起含 Qwen3 的 tool call 修正），加上對應的 cudart zip，兩包都含 sm_86。
    5. 用 llama-bench 掃參數。下載 Unsloth 的 UD-IQ3_XXS，從 --n-cpu-moe 34 往下掃，找到不溢位的最小值，再試 -ub 512、1024、2048。量 4K、32K、64K 的 prefill 和 decode，把數字填回這頁。也試一組「experts 全放 CPU（--n-cpu-moe 99）加 --moe-cache-mib 2500 --moe-cache-cpu-share 0.95」，跟固定 --n-cpu-moe 30 比 decode；scripts/moe-cache-tune.py 在 Windows 上會當掉（#32041），11/25 由 #32080 修好，但 11/26 最新的 b12728 還不含這個 commit；等下一個 b-build，之前先手動掃。
    6. 起 server。llama-server -m Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf --alias qwen3.6-35b-a3b --host 0.0.0.0 --port 8080 --api-key <自訂> -ngl 99 --n-cpu-moe 30 -c 65536 -ctk q8_0 -ctv q8_0 -np 1 -b 2048 -ub 2048 --ctx-checkpoints 12 --cache-ram 2048 --chat-template-file <修過的 Qwen 模板>。預設只聽 127.0.0.1，不加 --host 的話 Mac 連不進來；Windows 防火牆要開 8080。-np 1 很重要，預設的多個 slot 會把 KV 乘好幾倍。先從終端機手動啟動：Windows 會降低 Task Scheduler 和服務啟動的程式的磁碟優先權，Strata 實測讀模型因此慢約 15 倍。
    7. 接 Claude Code。Claude Code 跑在 Mac 上：ANTHROPIC_BASE_URL=http://<這台 IP>:8080、ANTHROPIC_AUTH_TOKEN=<上面的 key>、ANTHROPIC_MODEL=qwen3.6-35b-a3b、CLAUDE_CODE_MAX_CONTEXT_TOKENS=65536、CLAUDE_CODE_ATTRIBUTION_HEADER=0。背景請求也要指到同一個 ID（ANTHROPIC_DEFAULT_HAIKU_MODEL），否則會送出 Claude 的模型名稱。先用單檔修改的小任務測模板和工具呼叫。
    8. 顧散熱。長 prefill 和批次 OCR 都是滿載工作。整機峰值約 330–360W，SFX 電源要 450W 以上。可以用 nvidia-smi -pl 170（約 85%）換溫度，decode 幾乎不受影響：RTX 3090 從 350W 降到 250W，速度只從 32.0 變 31.7 tok/s，prefill 會慢一些。這個指令要系統管理員權限，重開機後會還原。

    風險與待確認

    • 沒有同規格的實測。沒人公開過 3060 Ti 8GB 配 16GB RAM 在 Windows 上跑 Qwen3.6-35B-A3B，最接近的都是 32GB RAM。這頁的速度和可用 context 都是推估。
    • RAM 很緊。13.5–15GB 的估計是關掉瀏覽器的情況。不夠時改 UD-Q2_K_XL（12.3GB），或把 context 降到 32K。
    • Compute buffer。8GB 卡上 -ub 2048 的 compute buffer 實際多大沒有資料；放不下就退回 1024 或 512，prefill 會掉到推估的下緣。
    • 3-bit 的精度。Qwen3.6-35B-A3B 的 3-bit GGUF 沒有公開的 KLD 或 agent 分數，Unsloth 只給圖。要自己對 Q8_0 算 KLD。
    • Prefix cache 和模板。#24055、#30357 修好之前（修正 PR #25592 還沒合併），每輪的 cache 命中率不可靠；修過的 Jinja 模板也沒有官方來源，Qwen 和 llama.cpp 到 11/19 都沒修。
    • CUDA crash。#26609：Windows、Qwen3.6、部分 experts 放 CPU、-fa on 時，第二個請求可能 illegal memory access，11/18 還有新回報；碰到就先試 -fa off。#31974：-ngl 固定時 --fit 不會幫忙縮，prefill 的 CUDA pool 不夠會整個 abort；-ub 2048 放不下就退回 1024。
    • 輔助機值不值得。Apple silicon 上 LLM 跟 embedding、OCR 同時跑會互相拖慢多少，沒有資料。NVIDIA 上有一筆：RTX 3090 同時跑時 embedding 吞吐降 8.6%、chat 降 11.8%。到貨後要自己量，再決定要不要多一次網路往返。
    • 硬體資訊。SSD、晶片組、RAM 速度、SFX 電源瓦數、Windows 版本和網卡速度還沒確認。
    • 什麼時候重新評估。llama.cpp 修好 hybrid 模型的 checkpoint（#24055、#30357）；有人公開 8GB 卡配 16GB RAM 的實測；Strata 把 Linux 的 file tier 搬到 Windows，或修好 #5285；出現放得進 8GB、agent 分數接近 Qwen3.6-35B-A3B 的新模型（SenseNova-Loop-9B 已經放得進 8GB，等 llama.cpp #32588 合併、有人量過它接 Claude Code 或 SWE-bench Verified 的成績）。
